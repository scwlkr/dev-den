- **documented**: Falcor rewrite and rediscovered edge cases. As a Netflix engineer, he rewrote another developer's request-deduplication code before understanding why it had its existing shape. As he encountered edge cases, his replacement converged on almost the same solution. His lesson is to investigate the constraints embodied in working code before replacing it, especially when the replacement must preserve production behavior. He separately endorses building a scratch implementation to learn a concept: the distinction is between a learning exercise and an unexamined production rewrite. The account is retrospective and does not establish that the old implementation was optimal. - **documented**: Falcor resource exhaustion. He reports discovering and reporting a vulnerability in which a compact request over large ranges, combined with materialization of missing paths, could create an enormous number of JVM objects and overwhelm the service. Because the behavior had existed in production for years, a simple recent rollback was not available. The operational lesson is to examine the ratio between request size and work or allocation induced, including adversarial inputs, rather than treating request count as the only denial-of-service risk. The transcript describes the mechanism but does not provide code or a complete remediation. - **documented**: Staging lockup from a concurrency assumption. - **documented**: Netflix recommendation indirection. He changed a TV-client data structure so a movie could have different recommendation explanations in different lists. Attaching the explanation directly to the movie made it shared everywhere; introducing a recommendation object associated the explanation with the movie's occurrence in a list. - **documented**: Game-server collision profiling. In his 2022 TypeScript server, a sampled CPU profile pointed to collision checking. He noticed bullets belonging to the same player could not collide and changed an all-pairs comparison to compare opposing players' bullets. - **documented**: Pooling in the same server. Allocation sampling identified message processing as a heavy source of short-lived objects even though it was not a dominant CPU hotspot. He built a reusable bullet pool and reports that, at 1,200 connections, good ticks rose from 64.2% to 74.7% and observed memory use fell. He also had to return objects and release resources when bullets or worlds ended. The lesson is to inspect allocation separately from CPU and measure the result; the limit is that pooling transfers lifetime and cleanup obligations to the programmer and can backfire under a JIT.
