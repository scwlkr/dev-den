- **documented**: Linux 5.3 I/O revert, 2019. As release maintainer, Torvalds reverted an I/O-pattern improvement that was not itself defective and had not changed an API. It exposed an unrelated existing bug, however, and a user's upgrade failed. His decision protected the working upgrade while alternative patches were discussed; he hoped to restore the improvement after agreement on the interaction. The case demonstrates that assigning blame for the underlying defect is not enough to decide what ships. The announcement does not fully establish the underlying interface or final fix. - **documented**: Sound configuration split, 2025. Reviewing a sound update, Torvalds reported that his laptop had lost HDMI and Realtek codec configuration. The old HDMI option had enabled everything, while the new split failed to preserve that outcome. He sketched defaults derived from the old option and a separate common-support symbol, while rejecting blanket enablement of genuinely new subdrivers. His example shows how to preserve prior intent during a configuration migration; it was illustrative, not a verified final patch, and he noted the additional difficulty of moving between revisions during bisection. - **documented**: BitKeeper to Git. Torvalds used BitKeeper because it supported kernel maintenance better than available alternatives. Distributed local repositories and merging changed his view of source control, despite problems with renames and its proprietary status. When continued use became untenable, he designed Git around distributed work, speed and integrity. Its rapid initial implementation followed substantial prior thought about the data model and other tools' shortcomings. The transferable lesson is to specify the real workflow before building; the kernel's scale and merge rate were particular requirements, not defaults for every project. - **documented**: Git handoff. After creating Git for his own kernel workflow, Torvalds selected Junio Hamano to maintain it. He describes observing clean solutions, judgment in patches and responses to other people's code, then credits Hamano with the sustained work that followed. The decision illustrates succession based on demonstrated technical judgment and commitment rather than founder control. It also limits any account that treats Git's later development as Torvalds's solo achievement. - **documented**: Custom waitlock review, 2009. Torvalds examined a proposed synchronization mechanism for asynchronous device suspend and resume. He identified ordering requirements on the decrement and wait paths and pointed out that atomic reads did not themselves provide the needed barriers. He proposed existing reader/writer semaphores, which also brought lockdep support and architecture-specific optimization. He then qualified his own analysis: one additional barrier might be unnecessary under the particular initialization and scheduling pattern. The lesson is to state both the general invariant and any usage-dependent exception; the proposed code is not evidence of a universally optimal implementation. - **documented**: Alpha page-table abstraction. Torvalds recalled that work for the Alpha port led to virtualizing page-table operations using macros and inline functions. The abstraction hid architectural differences, clarified the code and exposed earlier poor decisions; he said it improved x86 too without adding overhead in that case. His separate architecture explanation distinguished hardware page-table walks from software-managed translation mechanisms. This is a counterexample to the assumption that layering necessarily costs performance, not proof that every portability layer is free. - **documented**: Sparse user-pointer checking. Torvalds described needing to distinguish user-space pointers from kernel pointers without discarding each pointer's ordinary pointee type. After a request for a GCC solution did not produce one, he built a checking tool using an orthogonal annotation. He saw less need for an analogous physical-address annotation because those addresses were commonly represented as integers or page-frame numbers, making accidental dereference less likely. The lesson is to model the actual misuse and preserve existing type information, rather than introduce a generic category that loses it. - **documented**: Do-while macro misreading, 2008. After a kernel programmer misread an unbraced do-while macro, Torvalds argued for braces that make the final while visibly part of the construct. He added a sparse warning. The case connects a concrete review mistake to both a readability convention and tooling: familiar visual structure reduces the need to search backward for context. It does not establish that every possible style warning is worth adding or that formatting replaces semantic review. - **documented**: Release 2.5 retrospective. Asked about regrets, Torvalds criticized his own tendency to include more changes instead of producing stable releases more often. Larger change sets increased the amount of verification and debugging even though continuing development was more satisfying. He nevertheless valued central VM, block I/O and threading cleanups for maintainability as well as performance, while recognizing that users might care more about drivers. The case separates the value of the work from the cost of accumulating too much of it before stabilization. - **documented**: Xen backlog, 2008. In a discussion about development speed, Torvalds cited the large Xen patch backlog as exhausting existing reviewers and making the work too massive to attract easy additional review. He favored integrated exposure and asynchronous testing to get feedback sooner, while explicitly rejecting the idea that bad work should simply be merged. He was uncertain that throttling was the right answer and did not equate commit count directly with quality. The case cautions against treating a large private queue as a neutral holding area. - **documented**: Failing workstation memory. Torvalds recounted a machine that began producing kernel oopses and segmentation faults after years of operation. He spent days looking for a software bug before concluding the machine itself was unreliable. That experience informs his preference for ECC and a trustworthy development workstation. The lesson is to include the test environment in the fault model when failures are confusing; the anecdote alone does not show that every intermittent failure is caused by memory hardware. - **documented**: Old application version checks. Torvalds described programs that rejected a newer kernel version even though the application behavior was otherwise broken. The kernel provided a flag allowing an older version to be reported to affected programs. He acknowledged that this creates awkward compatibility code, but considered preserving the user's ability to run the application worthwhile. The case shows an exceptional workaround for deployed behavior, not a recommendation to conceal version information generally. - **documented**: Desktop SMP prediction. Torvalds acknowledged that he had once predicted symmetric multiprocessing would not be realistic on desktops. Processor integration changed the economics: two CPUs became nearly as cheap as one. He raised the mistake while discussing his continuing skepticism about the difficulty of general-purpose parallel programming. The useful distinction is between a prediction about hardware cost, which experience overturned, and a concern about reasoning and software structure, which he still held. Neither is a measurement of current multicore applications. - **documented**: Diffstat disagreement. Reviewing a clock-subsystem pull request, Torvalds investigated why its diffstat differed from his own. Copy detection approximated the numbers, but the accompanying create/delete summary did not consistently explain the apparent copies. Stephen Boyd explained that two different diff runs had been mixed, and Torvalds accepted the explanation. The practical lesson is to make summaries reproducible and internally consistent, then update the diagnosis when the producer supplies the missing context.
