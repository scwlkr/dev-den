# Linus Torvalds: frameworks

Built from 52 accepted distinct works and 220,774 source words. Compiled reasoning with source support and limits below.

- **inferred**: Unnamed: protect the working user workflow. First identify what existing users actually do, including reliance on incidental behavior. If a proposed feature or ordinary bug fix breaks that workflow, look for a compatible implementation; if the fix is not ready for release, revert the exposing change and revisit it. Serious security hazards can justify an exception, preferably with normal legitimate use preserved. This is a strong decision rule, not a promise that accidental regressions never happen. - **inferred**: Unnamed: release in stages, not around a feature wish list. Develop and test in subsystem and integration trees; merge work that is ready during a roughly two-week window; then spend roughly 6–8 weekly release candidates stabilizing. Disable or revert an unresolved late feature rather than make the release depend on it. The historical cadence is operational guidance, not a rigid law: holidays and confidence can change timing, and stable maintainers continue work after release. - **inferred**: Unnamed: pipeline quality and integration. Publish worthwhile work where others can test it in context, run integration and review asynchronously, and fix problems while other development continues. Do not interpret early exposure as permission to merge poor work. At release time, weigh a late fix against the risk that it introduces a new regression; a noncritical fix can wait for the next frequent release. Review counts alone are a weak substitute for actual review capacity. - **inferred**: Unnamed: network of trust for review and integration. Route changes through people with relevant subsystem and hardware knowledge. Build trust from their patches, their responses to other people's work and their sustained judgment; then accept that delegation includes decisions you might not personally make. At the top, read the explanation and history, expect prior review, and inspect conflicts for incompatible overlapping assumptions. This scales only if maintainers remain available and specialized knowledge is not isolated in one person. - **documented**: Unnamed: preserve published history while revising a series. If a branch was published without an expectation of rebasing, leave it intact and create a replacement from the common point. Compare old and new branches to show reviewers the change between series, or add fix commits to the old branch when that better serves collaborators. Merging both histories merely to retain them needs a specific benefit, such as preserving informative independent approaches or credit. - **inferred**: Unnamed: choose Git operations by publication and collaboration state. A private leaf developer can rebase a local queue; a maintainer should not casually rewrite other people's commits or present a freshly rebased tree as though earlier testing covered the new result. For a casual user without local commits, pulling upstream and inspecting a diff is simpler. If changes conflict, stay at the base, stash and reapply, or use commits and branches; none removes the need to resolve real conflicts. - **inferred**: Unnamed: assess the whole system before splitting a component. Map interactions, allocation dependencies, communication, coherence, ordering and debugging across the proposed boundary. Prefer the boundary with the simplest interface requirements, not the one that makes a single component look smallest. Shared layering can be valuable: VFS can centralize caching, serialization and mount traversal instead of duplicating them in each filesystem. The 2003 microkernel argument is a historical design judgment, not proof that isolation never pays. - **inferred**: Unnamed: reduce scope to make a difficult feature mergeable. List the valuable common case and the corner cases that create unresolved interactions. For the 2004 FUSE discussion, Torvalds suggested initially omitting shared writable mappings rather than pretending their dirty-page and memory-pressure problems were solved. Merge the understandable subset, then add omitted capability when its dependencies and failure modes are worked out. This is a sequencing choice, not a claim that the omitted feature is unimportant. - **inferred**: Unnamed: benchmark the cost that users actually pay. Reconstruct execution order, cache warmth, competing work and any costs displaced to another phase; then compare end-to-end behavior rather than treating an isolated operation as the product. In the 2000 page-zeroing discussion, hot and cold cache measurements were not directly comparable, and pre-initialization could move cache misses rather than eliminate them. Pre-initialization can still win when allocated pages are never subsequently touched. - **inferred**: Unnamed: investigate a suspicious profile, not just its hottest instruction. On the x86 system discussed in 2008, sampling could land after the costly operation because of interrupt delay and out-of-order execution. Examine nearby memory accesses, cache misses, branch mispredictions and earlier instructions delaying retirement; formulate alternatives before changing the sampled instruction. This is a diagnostic procedure for that profiling context, not a claim that every modern profiler has identical attribution behavior. ([linus-b523a1fcec4f83](https://yarchive.net/comp/linux/benchmarks.html) / evidence linus-b523a1fcec4f83-151d116d00ce; [linus-b523a1fcec4f83](https://yarchive.net/comp/linux/benchmarks.html) / evidence linus-b523a1fcec4f83-59792e70d50a; [linus-b523a1fcec4f83](https://yarchive.net/comp/linux/benchmarks.html) / evidence linus-b523a1fcec4f83-c4230a9fc1c4; 1 independent supporting works)

- **inferred**: Unnamed: choose synchronization by total cost and proof burden. Start with the ordering and atomicity required, then compare an established lock against a lock-free design including barriers, cache effects and architecture-specific behavior. Torvalds warned in 2005 that barriers can cost as much as locking and that subtle ordering mistakes are easy. In the 2009 device-resume example he proposed reader/writer locking to express parent-child ordering. Specialized cases can justify alternatives, but usage-dependent barrier assumptions need explicit examination. - **documented**: Unnamed: page-cache race protocol. Look up a page; if absent, allocate, look again and insert atomically only if it remains absent, discarding the spare allocation if another thread won. For a page needing data, check freshness, lock and recheck, initiate and wait for I/O only if still necessary, then return an error if it remains stale. This 2001 procedure illustrates double-checking after acquiring ownership and allowing retries; it is not a current kernel API recipe. ([linus-7a5e4bc6b5d93b](https://yarchive.net/comp/linux/page_cache.html) / evidence linus-7a5e4bc6b5d93b-8f26703c4fe0; [linus-7a5e4bc6b5d93b](https://yarchive.net/comp/linux/page_cache.html) / evidence linus-7a5e4bc6b5d93b-0d6ecfacda95; 1 independent supporting works)

- **inferred**: Unnamed: review readability by meaning and change history. Match surrounding style in shared code; give a specialized driver's likely maintainer more latitude. Separate a code move from cleanup so reviewers can verify behavior and history tools can follow it. Prefer direct tests that distinguish booleans from negative error codes, and keep useful error values. For dense code, inspect function size and indentation rather than blindly enforcing line length; his rolling-window idea was only a tentative signal. - **inferred**: Unnamed: make diagnostics useful under failure. Ask whether the condition can occur; if it can, prefer an accessible report and a recoverable error where possible. A driver BUG can leave locks held or make its diagnostic inaccessible. Reserve fatal handling for fundamental corruption with no workable recovery. Evaluate crash dumps separately for failure coverage, maintenance cost, disk-corruption risk and sensitive data exposure; controlled hardware can change that calculation. - **inferred**: Unnamed: evaluate large pages as distinct mapping and allocation problems. Separate TLB benefits from filesystem block, page-cache and I/O granularity. For giant pinned mappings, the 2002 proposal used explicit application selection and resource accounting because contiguous allocation, coherence and paging costs were substantial. Smaller superpages might be transparent, with fallback when a higher-order allocation fails. Compare latency and fragmentation across workloads; these historical proposals are not a description of current interfaces. - **inferred**: Unnamed: validate generated reports before transferring the burden. A human should investigate the suspected bug, propose a fix where possible, and remain available for discussion and revisions. A plausible generated report can consume substantial maintainer time if it is false, while a local patch can conceal a wider design problem. Treat AI review and prototypes as potentially useful inputs, not proof of correctness or a substitute for understanding maintained output.
