# Linus Torvalds: principles

Built from 34 accepted distinct works and 159,314 source words. Compiled reasoning with source support and limits below.

- **inferred**: Protect the user's working experience, not merely the formal ABI. An accidental dependency can still be a real regression, and a technically attractive feature should find a compatible route or wait. Serious security hazards and unsustainable obsolete-architecture support are qualified exceptions. Corroboration: high (3 distinct works; this measures source count, not truth). - **inferred**: Treat existing configuration as user work that must survive reorganization. Carry forward meaningful defaults, avoid enabling unrelated new functionality, and consider whether revision-to-revision testing loses configuration silently. If preservation is too difficult, reconsider the reorganization rather than transferring its cost to every user. Corroboration: low (1 distinct works; this measures source count, not truth). - **inferred**: Prefer steady releases of ready work to a date held hostage by a predetermined feature list. Keep a period of relative calm for stabilization, and defer a noncritical late fix when its regression risk exceeds the cost of waiting. A regular release does not imply that a cross-cutting feature can be implemented quickly. Corroboration: high (4 distinct works; this measures source count, not truth). - **inferred**: Delegate according to demonstrated judgment, and make the trust network reproduce itself. Review a maintainer's work and treatment of other people's changes, not merely their employer or tenure. Delegation includes accepting some decisions the top-level maintainer would have made differently; it should be accompanied by efforts to reduce single-person subsystem dependencies. - **inferred**: Evaluate architecture at system scope. A smaller component is not necessarily a simpler system if the split adds communication, coherence, state export and cross-domain debugging. - **inferred**: Demand a mechanism and representative workload before accepting a performance story. An isolated timing loop or warm lookup table can omit superscalar execution, cache competition or other costs that dominate the real workload. Processor-dependent branch behavior is a reason to test alternatives, not to assume one instruction always wins. Corroboration: high (3 distinct works; this measures source count, not truth). - **inferred**: Charge concurrency cleverness for its complete correctness and performance cost. Barriers, architecture-specific ordering and subtle assumptions about use can make a lock-free design expensive and fragile. Prefer a known primitive when it clearly expresses the required ordering; use specialized schemes only with an explicit argument for their guarantees and benefits. - **inferred**: Make code locally understandable before enforcing cosmetic uniformity. Prefer small functions, meaningful names and expressions that reveal whether a value is a boolean or an error. Match nearby shared code, but avoid style-only churn; rewriting or reformatting neglected code can still be worthwhile when it enables subsequent maintenance. - **documented**: Separate mechanical movement from cleanup. A reviewer can then check whether the move changed behavior, while history tools have a better chance of tracing the original code. Even whitespace-aware history has limits when edits split lines, so the separation is useful rather than a guarantee. Corroboration: low (1 distinct works; this measures source count, not truth). - **inferred**: Keep interfaces proportional to demonstrated need. A user-kernel interface is expensive to repair once applications depend on it, so require a real use case and weigh the enduring compatibility path against the gain. At the same time, a controlled escape hatch can be appropriate when a real workload needs capabilities a general abstraction hides. - **inferred**: Improve an existing system without assuming a clean rewrite will preserve its unnoticed strengths. Rewrite or replace internal pieces when needed, but identify the external behavior and hardware support that must remain. Incremental evolution is not a ban on major internal change; it is a way to retain feedback and compatibility while changing it. - **inferred**: Design collaboration tools around feedback latency and real integration volume. Distributed repositories make experimentation and local work easier, while fast merges leave more time for testing the result. The social process still matters: independent trees and cheap branches do not remove the need for trust, explanations and decisions about what to integrate. - **inferred**: Treat generated output as code someone must understand and maintain. Validate machine-generated reports before sending them, stay available for follow-up, and inspect whether a proposed patch addresses the underlying problem. This does not rule out useful automated review or throwaway prototypes; it changes the level of human responsibility required.
