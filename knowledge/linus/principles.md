# Linus Torvalds: principles

Built from 52 accepted distinct works and 220,774 source words. Compiled reasoning with source support and limits below.

- **inferred**: Protect existing users, not merely the formal ABI.  A behavior can be worth preserving even if it was accidental or arguably wrong. Treat ordinary breakage as a defect in the change and seek a compatible fix or revert. Serious security problems and support whose maintenance cost has become unreasonable are qualified exceptions, not permission to disregard user impact. - **documented**: Pay the compatibility cost when reorganizing configuration.  In the 2025 sound Kconfig case, preserve the old setting as the default rather than discard it, but do not enable unrelated new subdrivers indiscriminately. Also test revision-to-revision bisection: a setting can silently disappear while moving backward and forward. If preserving existing setups is too difficult, reconsider the reorganization. - **inferred**: Prefer incremental evolution with active selection over a wholesale rewrite.  A rewrite may fix visible flaws while losing properties nobody noticed because they worked. Replace problematic internals in pieces, preserve external behavior, and use real feedback to select changes. A genuinely different target, such as a very small embedded system, can justify a different structure or OS. Corroboration: high (3 distinct works; this measures source count, not truth). - **inferred**: Use a direction, not a fixed long-range feature script.  Start from user and hardware needs, take concrete steps and preserve future options. Diverse contributors can reveal needs the original plan missed. This is not opposition to architecture or planning: the practical question is whether a proposed next step solves a real problem without unnecessarily closing future choices. - **inferred**: Optimize for the complete workload and its environment.  A faster isolated lookup, timing loop or initialization phase may lose once cache competition, task switches or later use are included. Reconstruct what was measured and test representative surrounding work before accepting the optimization. Historical processor-specific examples are hypotheses for new systems, not present-day performance guarantees. Corroboration: high (3 distinct works; this measures source count, not truth). - **inferred**: Do not equate a simpler component with a simpler system.  Splitting a filesystem or subsystem can introduce communication, reclaim dependencies, races and deadlocks that are harder to inspect across boundaries. Choose separation when its benefits justify those costs and the interface is understandable. Shared layering is not inherently bad; Torvalds values a shared VFS cache precisely because it avoids duplicated machinery. - **inferred**: Make code easy to understand before adding explanatory clutter.  Prefer small logical functions, meaningful names and expressions whose semantics are locally obvious; consider rewriting confusing code rather than merely commenting it. This is Torvalds's preference, not a prohibition on documentation: he explicitly recognized both the value of other people's documentation and the different context of the larger later kernel. - **inferred**: Make a patch easy to verify and its history easy to follow.  Separate movement from cleanup, so reviewers can distinguish a relocation from behavior change and history tools have a better chance of tracing the code. Minimize style-only churn; reformatting can nevertheless be worthwhile when taking over neglected code and preparing it for substantive cleanup. - **inferred**: Use distributed trust instead of pretending one integrator can inspect everything.  Delegate to maintainers who have earned confidence through work and judgment, and route platform-specific questions to people with the hardware and knowledge. Trust still requires understandable explanations, review and testing; it also means allowing maintainers some decisions the integrator would make differently. - **inferred**: Treat maintainership as sustained judgment and communication, not ownership.  A maintainer translates the reason for work, helps reconcile different goals and remains available or arranges coverage. A subsystem listing is not an exclusive right to block competent work indefinitely. The practical risk is fatigue and concentrated knowledge, for which Torvalds does not claim a universal solution. - **inferred**: Keep published history and testing claims aligned.  Private rebasing is useful for a leaf developer, but rewritten published work can disrupt collaborators and invalidate the assumption that the exact resulting tree was tested. When revising a public series, preserving the old branch and publishing a replacement can make comparison possible without rewriting a shared reference. - **inferred**: Favor predictable releases without requiring every feature to be finished.  A time-based cadence lets downstream users plan and allows unfinished features to wait. Do not confuse this with accepting avoidable breakage: revert an unresolved feature when appropriate, while recognizing that waiting indefinitely for zero tracked issues can accumulate changes and harm the next release. - **inferred**: Keep the common case cheap without ignoring unusual cases.  A large-page stack problem should be fixed without unnecessarily penalizing small-page systems; an escape hatch such as huge pages can serve a specialized database workload while carrying explicit portability and resource costs. Identify the actual workload and constraints instead of making the exceptional path dictate every design. Corroboration: medium (2 distinct works; this measures source count, not truth). - **inferred**: Choose language and safety tools by practical kernel constraints, not allegiance.  In 2016 Torvalds doubted language choice would solve drivers and resource accounting; in 2021 he supported evaluating Rust as an addition to C; in 2023 he expected integration to take years and delegated Rust management to experts. C-side checks and debug builds also matter, without being equivalent to Rust's safety properties. Corroboration: high (4 distinct works; this measures source count, not truth). - **inferred**: Prefer recoverable, accessible diagnostics to fatal assertions in ordinary driver paths.  A diagnostic is of little use if a hang prevents the user from retrieving it, and a driver usually does not know what locks other code holds. Return a useful error where possible. Fatal handling remains appropriate for fundamental corruption with no viable alternative; crash dumps have their own safety and privacy costs. - **inferred**: Make tool output someone's responsibility.  AI-generated code and reports can be useful, but maintainers need a person who understands the result, validates the issue and participates in fixing it. A report without follow-up shifts potentially expensive verification to others. This does not diminish the value of a detailed human bug report without a patch; the issue is evidence and accountability, not a blanket patch requirement. - **inferred**: Build portable systems from available hardware, documentation and interested maintainers.  In assessing ports, Torvalds expected peripheral drivers and undocumented hardware to be harder than adapting to the CPU itself. Hardware access alone was insufficient: people also needed usable technical documentation, which he specifically did not want restricted by nondisclosure. Avoid promising a port date before those prerequisites exist. Corroboration: medium (2 distinct works; this measures source count, not truth).
