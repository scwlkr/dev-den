# Jonathan Blow: positions

Built from 80 accepted distinct works and 595,304 source words. Compiled reasoning with source support and limits below.

- **documented**: Language purpose: Jai is aimed at substantial systems and games, combining static typing, precompilation, control over the CPU, and limited automatic resource management. Blow wants expressive tools without making their costs mysterious. This is a domain choice, not a claim that every application needs manual management or that beginners are its primary audience. In 2025 he still described memory management as an explicit trade-off. - **documented**: C++ and migration: In 2014 Blow credited C++ for low-level access and performance while arguing that accumulated compatibility constraints burden newer features. He proposed incremental migration through C-compatible interfaces rather than rewriting a large engine at once. His comparison of Go, D, and early Rust belongs to that period and should not be treated as an assessment of their current versions. - **inferred**: Safety and experimentation: Blow supports catching memory errors but doubts that a mandatory restrictive ownership model is always the best trade for exploratory game development. Compare time spent satisfying constraints and compiling with time saved debugging over the project, while recognizing that rare, severe failures may be underrepresented in ordinary experience. He respects Rust's purpose and explicitly allows that its approach could prove him wrong. - **documented**: Ownership changed with experience: In 2014 Blow explored compiler-understood ownership annotations as a possible way to document and automate freeing. Later he reported removing a planned ownership feature after recognizing that fewer independently managed allocations and collectively reset temporary storage could avoid much ownership bookkeeping. The later account does not establish that ownership tracking is useless in every program. - **documented**: Entity lifetimes: For entities that can disappear or be paged out, Blow describes keeping IDs across frames and resolving them to pointers only within a known lifetime. A project-specific compile-time check can reject persistent entity pointers outside approved structures. This makes a concrete engine rule visible; it is not a proof of general memory safety, and he explicitly did not claim it was better than Rust. - **documented**: Data layout and allocation: Group data processed in the same way rather than assuming a custom allocator alone will fix scattered objects. Blow's concern about some RAII and reference-counting styles is partly that individually owned objects encourage dependent pointer reads and missed opportunities for batch processing. This is a workload-dependent critique, not a measurement that every use of either technique is slow. - **documented**: Temporary arenas and context allocators: A resettable arena makes short-lived strings and arrays convenient without individual frees, provided nothing survives its reset boundary. A shared context lets the caller substitute allocation and logging behavior for cooperating libraries. It does not automatically expose allocations hidden in external APIs, and crossing independently compiled boundaries can introduce unresolved context coordination. - **documented**: Garbage collection: Blow chooses manual control for his performance-sensitive games, especially where frame-time budgets and library allocations matter. He also places collection on a spectrum: the right choice for a nonprofessional user or a less timing-sensitive application may differ from a 120 or 240 Hz game. Pooling can reduce pauses but reintroduces explicit lifetime work. - **inferred**: Abstraction: An abstraction should reduce what a caller must understand, not merely move the same work behind a more general interface. Count synchronization and maintenance obligations as well as source lines. Blow nevertheless accepts useful factoring and domain-specific facilities; the practical question is whether their benefits survive contact with real code and edge cases. - **documented**: Feature scope: His 2014 partial-solution heuristic favors a simple mechanism covering common cases over a complicated universal one. The cited percentage was illustrative, not a measured acceptance threshold. He also permits redundancy when it materially improves debugging or daily ergonomics, so minimal feature count is not the objective by itself. - **documented**: Implicit behavior: Hidden behavior should pay for its loss of clarity. He prefers a diagnostic to silently allocating storage in an unresolved using case, and makes C-string conversion implicit for literals when a terminator can be supplied at compile time, but explicit when runtime copying is required. These are contextual boundaries rather than a blanket ban on implicit conversion. - **documented**: Static checking and diagnostics: Catch straightforward mistakes before execution, including undeclared names and application-specific invariants, but make the error explain the relevant use and its cause. Blow treats diagnostics as a language interface and wants source locations to survive compiler phases. Rich multiple-error recovery is desirable but requires suppressing cascades caused by placeholders. - **documented**: Metaprogramming: Jai exposes typed program information to user-level tools for generation, checking, and visualization. Blow regards this as useful for rules a general-purpose compiler cannot know, but warns that meta-level machinery increases comprehension costs. Use it where inspection or generation earns that complexity, and distinguish demonstrated facilities from proposals for future tools. - **inferred**: Compile-time execution and trust: Blow values unrestricted compile-time computation and acknowledges that downloaded build code can perform destructive operations. His exploration assumes trusted development contexts and compares the risk with existing build scripts; that does not make untrusted compilation safe. Isolation needs a separate threat-model decision, particularly for third-party plugins and dependencies. - **documented**: Polymorphism: He aims for convenient generic code resolved at compile time, so a small increase in generality need not force widespread template rewrites. Specializations can still cost build time and executable size; runtime dispatch is not the only cost to count. Inference is deliberately limited rather than an attempt to infer every constraint in every direction. - **documented**: Compiler architecture: Keep an internal representation under the compiler's control and translate to LLVM when that backend is requested. LLVM provides optimization and targets, but Blow reports significant integration and build costs; the native backend originally prioritized fast iteration rather than optimized output. His longer-term wish to reduce dependence on LLVM should not be confused with a claim that the optimizer had no value. - **documented**: Out-of-order compilation: Resolving declarations without source-order busywork improves the user model, but dependency scheduling, yielding, and polymorphism interactions have repeatedly generated compiler bugs. - **documented**: Build latency: Blow regards the edit–compile–debug cycle as a limit on thought, not merely a benchmark. - **documented**: Testing: Blow favors system-level tests for games and compilers because difficult failures often arise from interactions. - **documented**: Reproducibility: Deterministic execution aids debugging, but Blow does not want to prohibit every operation that could introduce nondeterminism. - **documented**: Quaternion interpolation changed in emphasis: His 2002 work explored fast slerp approximations and normalized linear interpolation.
