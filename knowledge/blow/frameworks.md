- **inferred**: Unnamed — Measure the ceiling before optimizing. Instrument the actual workload, separate inclusive from exclusive time, and compare each candidate with total elapsed time. Estimate the most it could save even if made free; then investigate why the work occurs before tuning instructions. Useful when a conspicuous routine or event attracts attention. In a 2018 build, parsing was about 25 ms of roughly 750 ms, so even eliminating it could not materially transform the build. That is a project-specific bound, not a general parser threshold. Reprofile after changes and include linking, which may dominate. - **inferred**: Interactive behavioral profiling. Keep low-overhead instrumentation available during normal development; observe frame timings beside the events that produced them; retain variance and distinguish self time from nested work. For recurring patterns, consider each frame's vector of zone timings rather than one session-wide average. Useful when intermittent pathfinding, rendering, or physics spikes disappear into averages. Choose smoothing according to the need for responsiveness versus stability, and use batch tools when precise averages or instruction-level measurements are the question. His proposed automatic behavior classification was exploratory, not a production guarantee. - **inferred**: Unnamed — Reduce, observe, discriminate. First construct a smaller failing example. List plausible explanations, instrument or break at the point that distinguishes them, and inspect actual values and compiler state before changing code. If execution order matters, disable threaded jobs, perturb the order with a seed, and replay that seed. For unstable identifiers, assert on the bad value instead of relying on a node number that changes between runs. Useful for compiler failures and other opaque state machines. A reproduced seed narrows the investigation; it does not establish that all schedules are fixed. - **inferred**: Unnamed — Make hidden computation observable. Implement a hard-to-inspect GPU transformation in software and verify the result visually before transferring it to the GPU. In a render pipeline, show intermediate targets and clear them conspicuously. If the intended visual channel is broken, map the same state to another visible property: Blow used square size to verify fog animation before debugging opacity. Use this when several stages could be wrong at once. A working software reference isolates the computation but does not prove the GPU version or its performance correct. - **inferred**: Unnamed — Find the authoritative representation. List each stored representation of a fact and the code that keeps them synchronized. Remove a redundant copy when the needed value can be derived cheaply and reliably; alternatively enforce the rule in a shared mechanism. Examples include deriving a beam's direction from its orientation and making an entity iterator skip objects awaiting destruction. Before deleting state, verify its lifetime: fading mirror projections can coexist, so they are not merely duplicate mirror data. Useful when editing or lifecycle changes repeatedly cause drift. - **inferred**: Unnamed — Test the language with the intended work. Identify the difficult real application and the feature whose value is in question. Build enough of that application using the feature itself, rather than wrapping or bypassing it; solicit feedback from people doing similar work; then incorporate feedback according to a coherent design direction. - **inferred**: The 85% solution. Start with a simple facility that solves common cases, define which cases it does not support, and give those cases an explicit alternative or error rather than accumulating exceptions to claim universality. The percentage is a heuristic, not measured coverage. Use it when a proposed general mechanism is becoming harder to understand than its concrete cases. Score by practical benefit, learning and debugging cost, implementation interactions, and whether the escape route is workable. Do not apply it mechanically where rare cases have unusually severe consequences. - **inferred**: Unnamed — Stage uncertain language decisions. Detect invalid or ambiguous cases and issue a useful error first. Where possible, try a user-level checker or macro, observe real use, and only then commit a rule to the compiler. If compatibility must change, run old and replacement mechanisms together, warn, and later remove the old one. Use this when the designer lacks enough experience to distinguish a genuine need from an attractive possibility. The closed-beta example used approximately a month between stages; that cadence is not a universal migration guarantee. - **inferred**: Unnamed — Localize complexity and preserve an upgrade path. For a broad redesign, build a simpler version first, but state how each simplifying assumption can later be removed. Keep unavoidable exceptional handling at a boundary rather than spreading it through common code. Blow began generalized LOD with height fields while requiring a credible path to arbitrary meshes; in compiler calls he moved foreign-varargs complexity toward the backend. Decide by total system complexity, not whether one phase becomes prettier. A credible path is a design obligation, not proof that the eventual generalization will be cheap. - **inferred**: Unnamed — Own and verify the shipped dependency set. For a substantial, long-lived application, keep the exact libraries and appropriate platform binaries with the project, update them deliberately, and let the application author decide overrides. Then build, package, distribute, and launch the actual artifact on a second machine. A content hash establishes identity, not continued availability; a clean machine can reveal missing headers and configuration. Use lighter workflows where vendoring is disproportionate, such as tiny programs. Local ownership also means accepting update, compatibility, and security-review work. - **inferred**: Unnamed — Encode project-specific lifetime rules. Describe the actual lifetime boundary, identify persistent structures that must not retain short-lived references, and enforce the rule with compiler-exposed typed program information. In Blow's entity example, retain an ID across frames, look up the entity, and handle absence; a metaprogram rejects entity pointers in non-whitelisted persistent structures. Useful when a general language cannot know an engine's destruction or paging semantics. This check is narrower than a complete memory-safety guarantee, and an incorrect whitelist or unexamined path can still defeat it. - **inferred**: Unnamed — Select a representation by invariants, not a single score. State what must remain exact, the tolerated worst-case error, input distribution, and resource budget. For scalar quantization, center reconstruction reduces bias under the stated random-input assumptions but cannot represent zero; rounded endpoint reconstruction preserves zero and one with a resolution cost. For rotations, choose nlerp, slerp, or another method according to velocity and blending requirements rather than optimizing slerp automatically. Useful for serialization, animation, and network bandwidth. Check degenerate cases and numerical domains explicitly. - **inferred**: Unnamed — Separate logical model from optimized query. Choose a unit whose constraints are intrinsic to the problem; write the simple, correct operation over it; then index or batch the operation that measurement shows to be expensive. In generalized LOD seams, a triangle touches at most three chunks because it has three vertices. Blow rewrites chunk-and-vertex references during simplification and treats runtime seam selection as a query that can later be indexed. Useful when a familiar hierarchy creates combinatorial casework. Precomputed combinations consume storage, so limiting LOD differences remains an option. - **inferred**: Unnamed — Budget an ambitious project in stages. Establish whether the team can already ship; inexperienced developers should generally complete shorter projects before spending five years on one. For an experienced team, explore the design with a minimal staff, scale production once the target is clearer, and consider releasing a large idea in installments. Evaluate quality against money, exhaustion, and delay rather than assuming either maximum ambition or minimum scope is always right. Blow's own experience includes both allowing a game to grow for its quality and later wishing he had chosen faster options more often. - **inferred**: Unnamed — Compare safety mechanisms over the project lifecycle. Specify the bug classes and severity that matter, then compare expected debugging and failure costs with the cost of restrictions, workarounds, compilation, and lost experimentation. Consider complementary checks: static project-specific invariants, bounds checks, and debug allocators that identify a free site. Useful when choosing a language or safety policy for a particular workload. Blow favors low-friction control for his games, but acknowledges that runtime checks require the faulty path to execute and are weaker than a correct complete static guarantee. His productivity comparison is a judgment, not a controlled measurement.
