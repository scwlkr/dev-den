- **inferred**: Choose abstractions by work actually removed, not by generality or shorter syntax. If callers still need to understand the concrete mechanism, and the abstraction adds indirection or configuration, prefer the concrete solution. Count synchronization duties, generated code, diagnostics, and maintenance as well as lines typed. A useful abstraction can still be worthwhile when it hides implementation without hiding consequential behavior. Corroboration: high (4 distinct works; this measures source count, not truth). - **inferred**: Optimize the workload, not the most interesting instruction. Measure total contribution, ask whether calls or data movement can be eliminated, and consider an algorithmic change before micro-optimization. - **inferred**: Design around data transformations and lifetime, not an assumed object hierarchy. Group data processed alike when the workload permits; distinguish allocation instruction cost from scattered accesses and cache misses. Use handles or temporary arenas where their lifetime rules fit. This is a workload-sensitive choice, not proof that every object-oriented design or garbage-collected application is slow. - **inferred**: Test interactions and actual release paths, not merely components in isolation. Preserve regression cases, exercise platform-specific code on the platform, and validate packaging on a second machine. Unit tests remain useful for selected difficult subproblems, and a passing integrated suite still covers only the paths exercised. Blow's skepticism concerns comprehensive unit testing as the default for his integrated games and compilers, not testing itself. - **inferred**: Judge performance by the user's actual failure mode, including tails and consistency. A good average can coexist with a bad frame, unfair input timing, or unacceptable worst-case quantization error. Instrument variability and test the states that produce it. This does not mean minimizing worst-case error regardless of cost: the appropriate metric depends on whether the application values visual quality, stable timing, exact endpoints, or bandwidth. - **inferred**: Use mathematical and architectural models to expose assumptions, then check their boundaries. A 2D line formula becomes a plane in 3D; a nearly singular intersection cannot be made robust merely by assuming an inverse exists; a rotation method must be chosen for its required properties. - **inferred**: Separate a successful result from understanding why it works. When a replacement random generator removes visible artifacts, examine its cost and whether its properties match the task; when tests pass despite scheduling-sensitive behavior, investigate before declaring the fix complete. This is especially important when duplicated fast and slow paths must agree. Under shipping pressure an imperfect workaround may be rational, but record that it remains imperfect. - **inferred**: Choose architecture for the problem and team, not identity with a methodology. ECS can address a general engine vendor's need to support unknown customer data, while a custom engine may not need the same machinery; component-style organization can be used selectively.
