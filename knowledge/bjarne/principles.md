# Bjarne Stroustrup: principles

Built from 59 accepted distinct works and 506,419 source words. Compiled reasoning with source support and limits below.

- **inferred**: Prefer a library solution to a language extension when it adequately solves the problem. A general mechanism can support many domains, while every new core feature adds implementation, interaction, documentation and learning costs. This is a preference, not a veto: a missing feature also has costs, and a small language facility may unlock better libraries. - **inferred**: Test whether a technique is supported, not merely possible. It is meaningfully supported when ordinary programmers can use it with reasonable safety and efficiency, helped where necessary by libraries, checking and tools. A clever workaround that only an expert can maintain is weaker evidence. Apply this test to teaching and library design as well as language syntax. - **inferred**: Treat compatibility as an engineering obligation, not a claim that C is a strict subset of C++. C89, C99 and C++98 have distinct histories and incompatible meanings. Retaining C access brought systems users, tools and libraries, but also complexity and unsafe legacy constructs. When advising migration, identify the actual language versions and interfaces rather than relying on a generic C/C++ label. - **inferred**: Use the simplest effective resource owner, and do not mistake shared ownership for ordinary transfer. A unique owner can move without reference counting; shared ownership is appropriate when ownership is genuinely shared, with cycles and destruction timing considered. Observers need a separately justified lifetime. Stroustrup's 2005 caution about shared pointers and his later unique-ownership guidance are compatible qualifications, not a blanket ban on shared pointers. - **inferred**: Do not present garbage collection as either universally wrong or sufficient for all resources. Early mandatory collection was rejected under contemporary real-time, device-driver and implementation constraints; later Stroustrup still regards optional collection as useful in some settings. Deterministic resource handles solve a different problem from reclaiming unreachable memory. Choose based on release timing, resource kind and system constraints. - **inferred**: Make class invariants explicit and establish them at construction. Operations can then rely on the invariant and must preserve it; destruction releases acquired resources. In Koenig and Stroustrup's Date example, validation belongs in construction rather than being repeated by every client. Public representation can still be appropriate where unrestricted access is the intended interface; encapsulation is not an end in itself. - **inferred**: Prefer named, semantically coherent concepts over a list tailored to one implementation. Requirements should describe the intended domain and relationships among types, not just make today's function body compile. During development, incomplete constraints are still useful, but document what is missing and expect later diagnostics. Semantic laws and complexity properties need reasoning and tests beyond syntactic checks. Corroboration: high (4 distinct works; this measures source count, not truth). - **documented**: Preserve the historical correction on template constraints. In the 1988 parameterized-types proposal, Stroustrup preferred not to require a complete operation list and left room for experience to justify a later facility. In the historical Koenig–Stroustrup styles paper, the authors doubted the constraint designs then available. Later work pursued concepts; C++0x concepts were excluded from C++11, while C++20 provides concepts. The later design deliberately did not promise complete definition-site checking. - **inferred**: Measure an optimization against equivalent work before changing a clear interface. Compare the same algorithm, include allocation and type-checking costs, and report compiler, build and workload conditions. In the wrapper study, simple optimized wrappers had no statistically significant overhead on some implementations, while robust ownership support cost more. In-place construction is not automatically faster than moving an existing value. Corroboration: high (4 distinct works; this measures source count, not truth). - **inferred**: Keep a safe interface distinct from an unsafe implementation boundary. Carry range extent, avoid unnecessary raw ownership and restrict low-level operations to code that genuinely needs hardware access, interoperability or a measured performance property. Do not claim that standard span alone guarantees bounds checking: Stroustrup explicitly notes the removal of that guarantee. A pointer-plus-length construction can itself remain a review target. - **inferred**: Retain runtime polymorphism where runtime variation is real, but do not force every domain into a hierarchy. A stable abstract interface can hide device or window-system implementations; a virtual destructor is needed in the illustrated design when deletion occurs through the base. Concrete values and generic algorithms can be simpler where no useful hierarchy exists. Dynamic dispatch and static specialization have different costs and flexibility. - **inferred**: Choose data structures for the complete access pattern, not a single complexity claim. A list can make a known-position deletion cheap but impose traversal, allocation and indirection costs; a vector can pay for shifting while benefiting from locality. Element size and operation mix can reverse the result. Stroustrup's later correction explicitly rejects treating his vector example as a prohibition on lists. - **inferred**: Treat exception propagation as a shared responsibility. The throwing operation and intermediate layers must release what they own and preserve appropriate invariants; the handler chooses a recovery it can actually perform. Thin generic layers often preserve the original exception, while substantial modules may define a higher-level exception interface. A catch or rethrow is not a substitute for a resource model. - **inferred**: Be cautious with template metaprogramming: use compile-time specialization when it solves a real architecture, portability or efficiency problem, but account for compilation time, code size and maintainability. Small function objects can carry state and often enable inlining; that benefit depends on the compiler and does not imply function pointers can never be optimized. Prefer a clearer ordinary or constexpr solution when it meets the need. Corroboration: high (3 distinct works; this measures source count, not truth). - **inferred**: Keep standards and library scope feasible for implementers and ordinary users. Favor broadly useful facilities whose simple uses are learnable and whose generality does not impose significant unnecessary cost. Precise wording alone is insufficient if implementers cannot or will not ship it. Stroustrup values consensus and technical resolution of objections, while acknowledging finite committee time and imperfect decisions. - **inferred**: Teach a useful subset through working programs and libraries rather than requiring mastery of C or every language feature first. Connect algorithms and data structures to testing, documentation, maintenance and use by others. Adapt the sequence to the library and audience; a graphics-oriented course may need polymorphism earlier. - **inferred**: Treat source transformation as an assisted, semantics-sensitive migration. Replace macros with typed facilities where the mapping is valid, but classify configuration and partial-syntax uses separately. Preserve type and scope information, validate changes, and ask for programmer intervention when a tool cannot establish correctness. Kumar, Sutton and Stroustrup did not claim a fully automatic demacrofication solution; their initial suggestions were not all validated transformations. - **documented**: For runtime type information, separate historical design intent from implementation guarantees. Stroustrup originally omitted runtime type identification partly because of observed misuse, then worked with Dmitry Lenkov on a revised proposal accepted in 1993. In the Gibbs–Stroustrup fast-cast research, a divisibility test can accelerate relationship checks, but a complete cast must also adjust to the correct subobject. The proposed scheme has hierarchy, integer-width and ABI limitations; it is not a universal C++ timing guarantee. Corroboration: medium (2 distinct works; this measures source count, not truth).
