# Bjarne Stroustrup: frameworks

Built from 81 accepted distinct works and 720,818 source words. Compiled reasoning with source support and limits below.

- **inferred**: Problem-driven language evolution — unnamed. Start with several real applications and reduce their problems to representative examples. Compare a language feature with library and tooling solutions, then check interactions with existing facilities, implementation feasibility, teaching, performance and migration. Prefer a solution that works now and can grow from feedback. Treat these as constraints, not a numerical score: a feature that solves one case beautifully but breaks deployed systems or cannot be implemented has not passed. Test the archetypes again against complete applications; optimizing only for small examples can mislead. - **inferred**: Compatibility and consensus — unnamed. Inventory affected source, compilers, libraries and users; estimate breakage, ease of recovery, long-term benefit and implementation cost. Prefer compiler-diagnosable breaks to silent changes, and consider compatibility switches or parallel interfaces. Breaking code is not forbidden, but needs a substantial benefit and a credible transition. For standards work, seek implementer acceptance as well as votes: Stroustrup describes roughly 90 percent support as comfortable and 80 percent as concerning, especially if a dissenting implementer is essential. Those are his practical heuristics, not formal voting thresholds. - **inferred**: Onion principle. Begin with a simple, safe interface that states the application’s intent. Measure the constraint that matters, then descend selectively through implementation choices, specialization and, if necessary, hardware-specific code. Each lower layer increases maintenance and error exposure, so retain the higher-level interface when possible. This is useful when a general abstraction is nearly adequate but a critical operation needs tuning. The decision threshold is demonstrated need, not an assumption that lower-level code is faster. A clean representation can also give the optimizer more useful information. ([bjarne-4e11090450bc3d](https://www.youtube.com/watch?v=2BuJjaGuInI&t=853) / evidence bjarne-4e11090450bc3d-9d455a30a294; [bjarne-f98c247fbbb5c2](https://www.youtube.com/watch?v=BMtLOKMUHsY&t=735) / evidence bjarne-f98c247fbbb5c2-ad3b8cbc96c8; [bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-d9e1d664c7a7; 3 independent supporting works)

- **inferred**: Zero-overhead evaluation — unnamed. Separate two questions: whether unused facilities impose costs and whether a used abstraction competes with a roughly equivalent hand-coded implementation. Compare the same algorithm and required guarantees, including allocation, code size and relevant compiler settings. A checked variant may legitimately cost more than an unchecked union because it provides a different guarantee. More specialized code can also win. In the pattern-matching experiments, Solodkyy, Dos Reis and Stroustrup used 101 timings and reported the median; the results varied by compiler and pattern, so that procedure is evidence for careful comparison, not a universal performance promise. ([bjarne-50dd598556cb0b](https://accu.org/journals/overload/29/161/stroustrup/) / evidence bjarne-50dd598556cb0b-d2d7e1e48477; [bjarne-4e11090450bc3d](https://www.youtube.com/watch?v=2BuJjaGuInI&t=1701) / evidence bjarne-4e11090450bc3d-249f1dbefd3f; [bjarne-0fb2730c7ce8f5](https://www.stroustrup.com/OpenPatternMatching.pdf) / evidence bjarne-0fb2730c7ce8f5-dffb545a8e8d; [bjarne-2d03fce9b4e490](https://www.stroustrup.com/wrapper.pdf) / evidence bjarne-2d03fce9b4e490-a369152b7590; 4 independent supporting works)

- **inferred**: RAII and lifetime operations. Identify each resource and its owner; have construction establish the invariant and destruction release the resource. Define or prohibit copying, and define moving when ownership must cross scopes. Assignment must also handle the destination’s old resource. Apply this to files, locks and sockets as well as memory, including early returns and exception unwinding. A container of raw pointers does not by itself own the pointed-to objects. Garbage collection can be useful, but does not replace timely, resource-specific cleanup. RAII also does not by itself prove that observers cannot dangle. ([bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-39db093291b9; [bjarne-94f225ac3002e4](https://www.stroustrup.com/except.pdf) / evidence bjarne-94f225ac3002e4-8bef9f38c632; [bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-dacd7ff3aab3; [bjarne-189b97e60bf82d](https://www.youtube.com/watch?v=ZO0PXYMVGSU&t=5523) / evidence bjarne-189b97e60bf82d-3bf1183ddbfb; 4 independent supporting works)

- **inferred**: Exception safety guarantees. First require the basic guarantee: invariants remain valid and resources do not leak. Ask which operations additionally need the strong guarantee, meaning success or unchanged state, and which must not throw. Construct a replacement before discarding a valid old representation where that makes rollback feasible. Dave Abrahams distilled these categories from standard-library work; Stroustrup treats RAII as necessary groundwork, not a complete guarantee. Evaluate element operations and destructor behavior too: a generic algorithm cannot promise recovery if user-supplied operations corrupt their operands or leak. ([bjarne-5877b33c3b0e61](https://www.stroustrup.com/DnE2005.pdf) / evidence bjarne-5877b33c3b0e61-304b18020433; [bjarne-94f225ac3002e4](https://www.stroustrup.com/except.pdf) / evidence bjarne-94f225ac3002e4-104ff8665678; [bjarne-783c826311cb99](https://www.stroustrup.com/eh_brief.pdf) / evidence bjarne-783c826311cb99-8822140cacd0; 3 independent supporting works)

- **inferred**: Error-policy selection — unnamed. Classify failure by frequency, recovery location and system constraints. Handle common, locally recoverable failures with tests or error values; consider exceptions for rare failures that must cross several layers, particularly when constructors or operators cannot conveniently return an error. Pair propagation with RAII and catch at a level that can act. For hard real time, measure or bound unwinding and cleanup rather than assuming exceptions are suitable. In unmanaged legacy code, first fix ownership or retain the existing strategy. Stroustrup later regretted presenting error handling too narrowly as exceptions. - **inferred**: Subset of a superset. First provide usable abstractions such as containers, spans and resource handles; then restrict hazardous direct operations in ordinary application code. State the desired guarantee, choose analyzable rules, and combine static checking with runtime checks where necessary. Keep narrowly scoped, reviewable exceptions for hardware access and the implementation of the abstractions themselves. Use this for gradual safety improvement in existing C++, not as a claim that all legal C++ is safe. A span carries extent, but the cited 2025 account notes that standard span alone did not guarantee range checking. - **inferred**: Local lifetime and invalidation analysis — unnamed. Identify owners, observers and possible escapes, including references hidden in containers and captures. Reject a pointer escaping a shorter-lived object; conservatively treat a call that may mutate a container as potentially invalidating its observers. Where available, a checked non-invalidating annotation can recover precision without requiring whole-program analysis. Use local analysis when speed and separate compilation matter, accepting that some safe programs will be diagnosed. The 2026 invalidation profile is a proposal, not an adopted guarantee, and delegates bounds and null checking elsewhere. - **inferred**: Generic-programming lift — unnamed. Start with working concrete algorithms, identify the operations and semantic assumptions they share, and parameterize the variable parts. Separate containers, iterators and algorithms; use half-open ranges so an empty range has equal endpoints. Then test generated code and document requirements. Generality can reduce a family of container-specific algorithms toward independently reusable components, but the product-to-sum comparison is illustrative rather than an exact accounting of every design. Credit Alexander Stepanov for the STL framework and the discipline of abstracting from working examples. - **inferred**: Concept design and overload selection — unnamed. Name a reusable domain idea, identify its operations, associated types and semantic laws, and express checkable requirements as concepts. Select the uniquely applicable constrained overload, or the more constrained one where the language’s subsumption rules establish an ordering; incomparable matches are errors. Use a random-access implementation and a forward-range fallback as a tuning pattern. Do not confuse syntactic satisfaction with proof of semantics: NaN is a counterexample to assuming that a less-than expression establishes a total order. Partial concepts can still help migration and development. - **inferred**: Multi-paradigm selection — unnamed. Use concrete value types for small domain concepts, generic programming for compile-time variation across types, and virtual interfaces when concrete implementations must be selected at runtime. Combine them when boundaries warrant it: a generic container can hold polymorphic shapes. The choice depends on when variation becomes known, required extensibility, checking, performance and maintainability. Avoid both a universal class hierarchy and elaborate templates where simpler code suffices. Generic code is not automatically faster on every architecture or compiler. - **inferred**: Hard-real-time feature assessment — unnamed. Identify the required response bound, then assess allocation history and fragmentation, dynamic-cast implementation, exception propagation depth and destructor work. Prefer static or scoped storage and appropriate pools when their timing is more predictable. Outside the most stringent hard-real-time systems, consider exceptions on their actual merits rather than banning them by reputation. In the 2005 machine-model paper, Stroustrup did not recommend them for hard real time without suitable predictive tools. Average speed or low normal-path cost is not a worst-case timing guarantee. - **inferred**: Teach backwards from useful work — unnamed. Choose a realistic initial project and derive the concepts students need to build it for other people. Introduce standard-library abstractions and error handling early, then explain the lower-level machinery through implementations of familiar types. Revisit invariants, interfaces, testing and maintenance in context. Adapt the sequence to the audience: experienced programmers need an overview, while beginners need programming fundamentals. Stroustrup reports using vector and string before pointers in his beginner course, but does not claim that order is universal or that his experience transfers directly to younger children.
