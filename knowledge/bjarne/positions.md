# Bjarne Stroustrup: positions

Built from 59 accepted distinct works and 506,419 source words. Compiled reasoning with source support and limits below.

- **documented**: Language evolution: Real problems, implementability, compatibility, teaching and transition paths are simultaneous constraints, not a formula that selects a feature automatically. In his 2007 history and 2021 summary, Stroustrup argues that a language must remain useful throughout change. A proposal can be attractive in isolation yet fail because existing code, compilers or users cannot migrate. Conversely, preserving every historical choice can lead to stagnation. ([bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-0a45881281d2; [bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-b6a90dc7db59; [bjarne-50dd598556cb0b](https://accu.org/journals/overload/29/161/stroustrup/) / evidence bjarne-50dd598556cb0b-2231c641055a; 2 independent supporting works)

- **inferred**: Zero-overhead abstraction: Unused facilities should not impose costs, and used abstractions should be competitive with roughly equivalent hand-written code. This is a design goal, not a promise that every abstraction beats a more specialized implementation or that every compiler optimizes it equally. In a performance dispute, identify equivalent functionality, include allocation and code size, and measure the actual build. Preserve direct hardware access when it is genuinely needed. ([bjarne-36aa60d256697d](https://www.stroustrup.com/abstraction-and-machine.pdf) / evidence bjarne-36aa60d256697d-eb7d83afc2b5; [bjarne-50dd598556cb0b](https://accu.org/journals/overload/29/161/stroustrup/) / evidence bjarne-50dd598556cb0b-d2d7e1e48477; [bjarne-2d03fce9b4e490](https://www.stroustrup.com/wrapper.pdf) / evidence bjarne-2d03fce9b4e490-a369152b7590; 3 independent supporting works)

- **documented**: Libraries versus language features: Prefer a general mechanism plus a library when it solves the real problem adequately. Library abstractions can give users domain vocabulary without creating a dialect, but they still demand implementation, documentation, teaching and generality. The 1992 extensions working group treated an existing implementation as useful evidence, not sufficient grounds for standardization. A missing feature has costs too, so rejection is not automatic. ([bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-2377b4cb4c54; [bjarne-7e06ae970694d2](https://www.stroustrup.com/how-to-write-a-proposal.pdf) / evidence bjarne-7e06ae970694d2-e86cb9e30f70; [bjarne-7e06ae970694d2](https://www.stroustrup.com/how-to-write-a-proposal.pdf) / evidence bjarne-7e06ae970694d2-835d110dd40e; [bjarne-37bf63a3e7ed2b](https://www.artima.com/articles/a-brief-look-at-c0x) / evidence bjarne-37bf63a3e7ed2b-0c1e2edc841b; 3 independent supporting works)

- **documented**: C compatibility: C provided systems access, implementations and an existing user community, but also imposed lasting complexity and safety constraints. C is not a strict subset of C++, and C99 and C++ are sibling languages rather than a single language. His 2002 compatibility case studies include conditional proposals to accept some safety compromises as part of a broader agreement; those proposals are not evidence that the changes were adopted. ([bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-eaf93f4c9a4e; [bjarne-6d78140a0c291c](https://www.stroustrup.com/bs_faq.html) / evidence bjarne-6d78140a0c291c-88edc4a3cacb; [bjarne-24c2873fa1e034](https://www.stroustrup.com/examples_short.pdf) / evidence bjarne-24c2873fa1e034-b001854cbc2b; [bjarne-975f3ec440d433](https://www.stroustrup.com/siblings_short.pdf) / evidence bjarne-975f3ec440d433-08e4832d8058; 4 independent supporting works)

- **documented**: Breaking changes: Compatibility is a strong constraint, not an absolute veto. In the 2002 C and C++ case studies, he evaluates breakage by its extent, recovery cost, long-term benefit and implementation difficulty. A change is easier to defend when the old usage is obscure or error-prone and a compiler can diagnose affected code. Silent changes in meaning require particular caution; compatibility switches may help preserve unchanged legacy source. ([bjarne-24c2873fa1e034](https://www.stroustrup.com/examples_short.pdf) / evidence bjarne-24c2873fa1e034-7ae85edb0055; [bjarne-24c2873fa1e034](https://www.stroustrup.com/examples_short.pdf) / evidence bjarne-24c2873fa1e034-d9337d6aff53; [bjarne-24c2873fa1e034](https://www.stroustrup.com/examples_short.pdf) / evidence bjarne-24c2873fa1e034-15cd57646020; 1 independent supporting works)

- **documented**: Multiple programming styles: Use runtime polymorphism where concrete types must vary at runtime, generic programming where operations can be selected statically, and ordinary concrete types or functions where neither mechanism is needed. A generic container of polymorphic shapes can combine the approaches. Stroustrup warns both against forcing every problem into a class hierarchy and against making template machinery a universal replacement; composing styles systematically remains difficult. ([bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-d372b57c21e1; [bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-60151408f37f; [bjarne-6d78140a0c291c](https://www.stroustrup.com/bs_faq.html) / evidence bjarne-6d78140a0c291c-517f6f7b83ce; [bjarne-8499a11781ef93](https://www.stroustrup.com/Concept-based-GP.pdf) / evidence bjarne-8499a11781ef93-470b9c90ee91; 3 independent supporting works)

- **documented**: Concrete types and invariants: A constructor should establish the conditions member functions rely on; operations should preserve them, and an owning destructor should release resources. Small types such as dates or units can express application concepts without requiring a hierarchy. Encapsulation is useful when unrestricted mutation would break an invariant, but representation need not be hidden when unrestricted access is the intended contract. ([bjarne-3d5d545f1e6ccf](https://www.stroustrup.com/style95.pdf) / evidence bjarne-3d5d545f1e6ccf-d8b428208f70; [bjarne-3d5d545f1e6ccf](https://www.stroustrup.com/style95.pdf) / evidence bjarne-3d5d545f1e6ccf-5c0d9bd896a2; [bjarne-6d78140a0c291c](https://www.stroustrup.com/bs_faq.html) / evidence bjarne-6d78140a0c291c-b57156585e80; 2 independent supporting works)

- **documented**: RAII and garbage collection: Bind a resource to a handle whose lifetime controls release, including on exception paths. This applies to files and locks as well as memory. Stroustrup rejected mandatory collection for early real-time and driver users but has also said optional collection can be useful; he does not claim that a collector is never appropriate. Collection of memory alone does not ensure timely, resource-specific release. ([bjarne-faf11ea2080fa8](https://www.stroustrup.com/hopl2.pdf) / evidence bjarne-faf11ea2080fa8-2cfebd9f4211; [bjarne-faf11ea2080fa8](https://www.stroustrup.com/hopl2.pdf) / evidence bjarne-faf11ea2080fa8-d4b092795b1f; [bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-772d113442fd; [bjarne-ebfe802dabed13](https://www.stroustrup.com/resource-model.pdf) / evidence bjarne-ebfe802dabed13-5181f3ac27e1; 3 independent supporting works)

- **documented**: Ownership and moves: Prefer unique ownership for a resource that is transferred rather than genuinely shared; use shared ownership when multiple owners are actually required and address cycles where relevant. Move operations transfer resources, while copy operations reproduce values. A named rvalue-reference parameter is itself an lvalue expression, so a deliberate move is needed when transferring from it. The 2008 tutorial is coauthored with Howard Hinnant and Bronek Kozicki. ([bjarne-4a995c56f1ad83](https://www.stroustrup.com/what-is-2009.pdf) / evidence bjarne-4a995c56f1ad83-99c767282d51; [bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-39db093291b9; [bjarne-065773b9938c58](https://www.artima.com/articles/a-brief-introduction-to-rvalue-references) / evidence bjarne-065773b9938c58-c6391193c03c; [bjarne-065773b9938c58](https://www.artima.com/articles/a-brief-introduction-to-rvalue-references) / evidence bjarne-065773b9938c58-6d1307470618; 3 independent supporting works)

- **documented**: Exception policy: Use error values and local tests when failure is common and can be handled locally; use exceptions when a rare failure must cross intervening layers to a handler that can respond. Before propagation, preserve valid state and release owned resources. The earlier proposal with Andrew Koenig also allows cooperative callbacks where resumption is appropriate. Hard-real-time constraints can change the choice because unwinding time may be difficult to bound. ([bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-9ef6b6a6ae2d; [bjarne-259ce62357d855](https://www.stroustrup.com/except89.pdf) / evidence bjarne-259ce62357d855-1fb41db7f5b6; [bjarne-36aa60d256697d](https://www.stroustrup.com/abstraction-and-machine.pdf) / evidence bjarne-36aa60d256697d-d6661b025c08; 3 independent supporting works)

- **documented**: Exception guarantees: Aim for valid invariants and no resource leaks after failure; offer unchanged state where the operation and its cost justify the stronger guarantee, and no-throw behavior for suitable operations. Dave Abrahams distilled these guarantees from library-group work. They depend on assumptions about supplied operations and destructors; a valid container may still be empty or unsorted, so validity is not identical to application recovery. ([bjarne-5877b33c3b0e61](https://www.stroustrup.com/DnE2005.pdf) / evidence bjarne-5877b33c3b0e61-304b18020433; [bjarne-94f225ac3002e4](https://www.stroustrup.com/except.pdf) / evidence bjarne-94f225ac3002e4-104ff8665678; [bjarne-783c826311cb99](https://www.stroustrup.com/eh_brief.pdf) / evidence bjarne-783c826311cb99-d87cae83a6d3; 3 independent supporting works)

- **documented**: Generic requirements and concepts, old and new: In the 1988 template proposal, Stroustrup preferred not to require a complete operation list on a class template, preserving use with unordered element types. In the historical paper with Andrew Koenig, the authors also doubted whether then-conceived constraints could be sufficiently flexible. Later he advocated named concepts for clearer interfaces and diagnostics; C++0x concepts were excluded from C++11, while C++20 provides concepts. ([bjarne-b1a888823a69fd](https://www.stroustrup.com/parameterized_types_1988.pdf) / evidence bjarne-b1a888823a69fd-160df6185bcf; [bjarne-3d5d545f1e6ccf](https://www.stroustrup.com/style95.pdf) / evidence bjarne-3d5d545f1e6ccf-470682c55eb5; [bjarne-3d46d0054df96a](https://www.stroustrup.com/sle2010_webversion.pdf) / evidence bjarne-3d46d0054df96a-b5faef811662; [bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-6e2e0a4876f2; 4 independent supporting works)

- **documented**: Concept semantics: A useful concept represents a meaningful abstraction and relationships among types, not merely a list of operators accidentally used by one implementation. Syntactic checking cannot establish all semantic laws: a less-than expression alone does not establish an appropriate ordering in the presence of NaNs. With Andrew Sutton, Stroustrup distinguishes checkable constraints from assumed axioms. Incomplete concepts remain useful during migration, although some errors then appear only at instantiation. ([bjarne-72241b845beaaf](https://www.stroustrup.com/sle2011-concepts.pdf) / evidence bjarne-72241b845beaaf-dbdda40d2c71; [bjarne-72241b845beaaf](https://www.stroustrup.com/sle2011-concepts.pdf) / evidence bjarne-72241b845beaaf-e69f8cfa27fe; [bjarne-b23c7274491b67](https://www.stroustrup.com/good_concepts.pdf) / evidence bjarne-b23c7274491b67-35649ba498f3; [bjarne-b23c7274491b67](https://www.stroustrup.com/good_concepts.pdf) / evidence bjarne-b23c7274491b67-82494ff4174c; 2 independent supporting works)

- **documented**: Definition checking for concepts: The 2005–2006 work sought complete checking of template definitions against declared requirements. By the 2017 Concepts TS account, Stroustrup explains that he, Gabriel Dos Reis and Andrew Sutton deliberately did not require that check initially, prioritizing point-of-use feedback and gradual adoption. Undeclared implementation needs can therefore still produce later errors. These are distinct designs and should not be conflated. ([bjarne-5877b33c3b0e61](https://www.stroustrup.com/DnE2005.pdf) / evidence bjarne-5877b33c3b0e61-1007c6f77705; [bjarne-7549649ab55288](https://www.stroustrup.com/popl06.pdf) / evidence bjarne-7549649ab55288-924b2ce2b1c2; [bjarne-b23c7274491b67](https://www.stroustrup.com/good_concepts.pdf) / evidence bjarne-b23c7274491b67-3e64cafb8385; 3 independent supporting works)

- **documented**: Containers and algorithms: Separate algorithms from containers through iterators or ranges with stated operational requirements. This supports reuse across unrelated representations and can reduce duplicated algorithm definitions. Non-intrusive value containers avoid some allocation and indirection costs, but insertion may copy an element; pointers can be preferable for expensive-to-copy objects. An iterator-based design is more general than keeping one traversal position inside a container, though the simpler design can suffice in restricted cases. ([bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-c1b5ac452741; [bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-4a72798f7864; [bjarne-12e9033e1f6671](https://www.stroustrup.com/whatis.pdf) / evidence bjarne-12e9033e1f6671-be8e74f9d943; [bjarne-5877b33c3b0e61](https://www.stroustrup.com/DnE2005.pdf) / evidence bjarne-5877b33c3b0e61-2a58ed4f16ea; 3 independent supporting works)

- **inferred**: Data layout and container choice: Start with compact, predictable memory access, often contiguous storage, then test the actual access pattern. Traversal and cache misses can dominate the nominal complexity of insertion or deletion. Stroustrup explicitly rejects a universal ban on lists: large elements or operations such as front insertion can change the result. Compare the whole workload rather than carrying over a result from his particular vector-and-list exercise. ([bjarne-6d78140a0c291c](https://www.stroustrup.com/bs_faq.html) / evidence bjarne-6d78140a0c291c-a43fe08fba8b; [bjarne-c9839d4ff3a827](https://isocpp.org/blog/2014/06/stroustrup-lists) / evidence bjarne-c9839d4ff3a827-fc50f5b4249b; [bjarne-c9839d4ff3a827](https://isocpp.org/blog/2014/06/stroustrup-lists) / evidence bjarne-c9839d4ff3a827-a5da1e6ae3f9; [bjarne-7db324a86881a5](https://www.stroustrup.com/improving_garcia_stroustrup_2015.pdf) / evidence bjarne-7db324a86881a5-9f70dcd4cd8d; 3 independent supporting works)

- **inferred**: Template metaprogramming: Compile-time selection can make portable libraries fast and remove runtime machinery, but sophisticated templates can produce obscure code, long compilation and code bloat. Stroustrup acknowledges techniques he did not anticipate and does not reject the underlying capability. Use the simplest understandable mechanism that meets the need; for computing values, he points to constexpr as a clearer alternative in suitable cases. ([bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-1a7141c5690f; [bjarne-6d78140a0c291c](https://www.stroustrup.com/bs_faq.html) / evidence bjarne-6d78140a0c291c-bb31e4a2f345; [bjarne-6d78140a0c291c](https://www.stroustrup.com/bs_faq.html) / evidence bjarne-6d78140a0c291c-dc98427ca16c; [bjarne-b1a888823a69fd](https://www.stroustrup.com/parameterized_types_1988.pdf) / evidence bjarne-b1a888823a69fd-bba192815414; 3 independent supporting works)

- **documented**: Hard real time: Average speed is not enough when a deadline needs a defensible bound. Allocation can depend on allocation history, and exception propagation on unwinding depth and destructors; RTTI implementation also matters. In the 2005 machine-model paper he does not recommend exceptions for hard real time without suitable predictive tools. Elsewhere he recommends considering exceptions outside the most stringent cases. These positions depend on the timing requirement and implementation, not a blanket feature ban. ([bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-0cfbbe01b1d4; [bjarne-36aa60d256697d](https://www.stroustrup.com/abstraction-and-machine.pdf) / evidence bjarne-36aa60d256697d-d6661b025c08; [bjarne-5877b33c3b0e61](https://www.stroustrup.com/DnE2005.pdf) / evidence bjarne-5877b33c3b0e61-9ee93e93ca38; [bjarne-be42606566c159](https://www.stroustrup.com/fdc_jcse.pdf) / evidence bjarne-be42606566c159-5d29332359e4; 4 independent supporting works)

- **documented**: RTTI: Stroustrup originally omitted runtime type identification because type tests were often misused as switches. He later supported a standard mechanism, with Dmitry Lenkov, after incompatible library-specific approaches and interface-crossing needs became apparent. Pointer dynamic_cast reports failure with null; a reference cast throws. The mechanism is intentionally more limited than full reflection, whose metadata costs may be unsuitable for some applications. ([bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-f4ad2ad17b2c; [bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-a12f24851a24; [bjarne-ce86a57fb55247](https://www.stroustrup.com/crc.pdf) / evidence bjarne-ce86a57fb55247-def61195abc1; 2 independent supporting works)

- **documented**: Concurrency: A systems language needs primitives and a memory model that allow multiple higher-level concurrency models rather than hardwiring one model. Threads and locks are necessary but difficult; futures can be cleaner for suitable independent tasks. Lock-free algorithms require specialist reasoning about both progress and correctness. Work with Damian Dechev compares CAS and transactional implementations for particular embedded workloads, not as a universal rejection of transactions. ([bjarne-4a995c56f1ad83](https://www.stroustrup.com/what-is-2009.pdf) / evidence bjarne-4a995c56f1ad83-cd9a87462438; [bjarne-4a995c56f1ad83](https://www.stroustrup.com/what-is-2009.pdf) / evidence bjarne-4a995c56f1ad83-1b5060d2d712; [bjarne-42c5d271888cb3](https://www.stroustrup.com/smc_it2009.pdf) / evidence bjarne-42c5d271888cb3-6ade4df13494; [bjarne-42c5d271888cb3](https://www.stroustrup.com/smc_it2009.pdf) / evidence bjarne-42c5d271888cb3-1481605eb252; 2 independent supporting works)

- **documented**: Safety profiles: The 2021 and 2025 accounts propose combining safer library abstractions, restricted usage, local static analysis and runtime checks where necessary. Lifetime analysis must consider escapes and invalidation, including pointers hidden in objects. Conservative assumptions can reject safe programs; carefully validated annotations may improve precision. Low-level hardware code needs narrowly scoped, reviewable exceptions. These proposals are not evidence that a complete standardized safety regime has been adopted. ([bjarne-ba011de2f93d22](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2021/p2410r0.pdf) / evidence bjarne-ba011de2f93d22-5dbe1fe4a278; [bjarne-ba011de2f93d22](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2021/p2410r0.pdf) / evidence bjarne-ba011de2f93d22-6dbc5fc9069a; [bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-ef2d3eae13a3; [bjarne-ebfe802dabed13](https://www.stroustrup.com/resource-model.pdf) / evidence bjarne-ebfe802dabed13-0f16fb7c7f9b; 3 independent supporting works)

- **documented**: Bounds and spans: An extent-carrying range is preferable to a bare pointer when a function needs indexed access, because the boundary becomes available to checking and review. Stroustrup distinguishes the range-checked GSL facility discussed in 2021 from standard span: in his 2025 account, standard span does not itself guarantee range checking. A pointer plus an explicit length can still be wrong, so carrying an extent is not a complete proof of safety. ([bjarne-ba011de2f93d22](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2021/p2410r0.pdf) / evidence bjarne-ba011de2f93d22-2b39cee4798f; [bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-880a67a8640c; [bjarne-8499a11781ef93](https://www.stroustrup.com/Concept-based-GP.pdf) / evidence bjarne-8499a11781ef93-1673273d7f28; 3 independent supporting works)

- **documented**: Modules and compilation boundaries: Modules address textual headers, order dependence and repeated compilation, but migration of a substantial code base has real costs and reported speedups vary. Earlier, Stroustrup supported separately compiled templates to protect implementation boundaries, while later conceding that opponents of export were right about implementation complexity and that the compromise delivered only some expected benefits. Modules are a complementary organization mechanism, not a consequence of concepts alone. ([bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-09f13ea379cc; [bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-e57ee77ce1a9; [bjarne-b23c7274491b67](https://www.stroustrup.com/good_concepts.pdf) / evidence bjarne-b23c7274491b67-cad64256b593; 3 independent supporting works)

- **documented**: Embedded subsets: Select facilities appropriate to a target, but be wary of a separate dialect that removes templates or cannot support the standard library. Stroustrup argues that such dialects split libraries, tools and communities and may discard useful embedded techniques. His objection does not mean that every Standard C++ feature is suitable for every device: allocation, exceptions and RTTI must still be assessed against the actual constraints. ([bjarne-5877b33c3b0e61](https://www.stroustrup.com/DnE2005.pdf) / evidence bjarne-5877b33c3b0e61-98d754767a53; [bjarne-6d78140a0c291c](https://www.stroustrup.com/bs_faq.html) / evidence bjarne-6d78140a0c291c-d0ee21fac0f3; [bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-9313144f052f; 3 independent supporting works)

- **documented**: Teaching: Introduce useful standard-library abstractions and programming concepts early rather than requiring mastery of C first. Work from concrete examples toward design, then use familiar library implementations to explain pointers and allocation. Adapt the order to students and projects; a graphics-based course may need polymorphism earlier. His 2009 curriculum account is based on experience without controlled evidence of effectiveness, and he acknowledges a shortage of accessible introductory graphics facilities. ([bjarne-f8c2555fc934a2](https://www.stroustrup.com/new_learning.pdf) / evidence bjarne-f8c2555fc934a2-c07deddb68ea; [bjarne-f8c2555fc934a2](https://www.stroustrup.com/new_learning.pdf) / evidence bjarne-f8c2555fc934a2-71b0bf92e762; [bjarne-f8c2555fc934a2](https://www.stroustrup.com/new_learning.pdf) / evidence bjarne-f8c2555fc934a2-46ac5383a37e; [bjarne-29a41371235521](https://www.stroustrup.com/software.pdf) / evidence bjarne-29a41371235521-a972274e12a5; 2 independent supporting works)
