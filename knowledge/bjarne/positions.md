# Bjarne Stroustrup: positions

Built from 81 accepted distinct works and 720,818 source words. Compiled reasoning with source support and limits below.

- **inferred**: Systems-language fit. C++ is most compelling when a system needs both direct hardware use and substantial management of complexity. If one requirement is absent, another language may be a better choice. Evaluate the whole environment, including available libraries, tools, deployment constraints and maintainers, rather than treating language selection as a contest over syntax alone. ([bjarne-5bb9fffa04ec44](https://stroustrup.com/TechRepublic-interview-Bjarne-Stroustrup.pdf) / evidence bjarne-5bb9fffa04ec44-74ecce7d4750; [bjarne-d85e3e25027cfd](https://stroustrup.com/Italian-Interview-2023.pdf) / evidence bjarne-d85e3e25027cfd-ae567cdf0f35; [bjarne-f98c247fbbb5c2](https://www.youtube.com/watch?v=BMtLOKMUHsY&t=334) / evidence bjarne-f98c247fbbb5c2-6c9ed07a22c3; 3 independent supporting works)

- **inferred**: Zero-overhead abstraction. The design target has two parts: unused facilities should not impose costs, and used abstractions should compete with roughly equivalent hand-written code. It is not a promise that every check is free or that a more specialized implementation cannot be faster. A checked variant may pay for a tag test because it provides a capability an unchecked union does not. ([bjarne-36aa60d256697d](https://www.stroustrup.com/abstraction-and-machine.pdf) / evidence bjarne-36aa60d256697d-eb7d83afc2b5; [bjarne-50dd598556cb0b](https://accu.org/journals/overload/29/161/stroustrup/) / evidence bjarne-50dd598556cb0b-d2d7e1e48477; [bjarne-4e11090450bc3d](https://www.youtube.com/watch?v=2BuJjaGuInI&t=1701) / evidence bjarne-4e11090450bc3d-249f1dbefd3f; 3 independent supporting works)

- **inferred**: Language evolution and compatibility. He balances simpler use, additional expressive power and stability for deployed code. Supply an effective replacement before discouraging an old facility; consider removal only with a credible transition. Compatibility is not absolute: a break is more defensible when the benefit is substantial, the affected usage is error-prone, and compilers can diagnose the break rather than silently change meaning. ([bjarne-011a23f6854d67](https://www.youtube.com/watch?v=ixmDTTDiEDE&t=522) / evidence bjarne-011a23f6854d67-6d51da9f77c5; [bjarne-3d5d545f1e6ccf](https://www.stroustrup.com/style95.pdf) / evidence bjarne-3d5d545f1e6ccf-9102ea35ab39; [bjarne-24c2873fa1e034](https://www.stroustrup.com/examples_short.pdf) / evidence bjarne-24c2873fa1e034-d9337d6aff53; 3 independent supporting works)

- **documented**: C compatibility. Choosing C brought hardware access, implementations, tools and users, but also inherited complexity and unsafe conventions. C is not a strict subset of C++; the relationship differs across historical C versions. His 2002 suggestion to accept implicit void-pointer conversions was a conditional sacrifice for a comprehensive compatibility agreement, not a statement that this became C++ or that type safety is unimportant. ([bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-eaf93f4c9a4e; [bjarne-6d78140a0c291c](https://www.stroustrup.com/bs_faq.html) / evidence bjarne-6d78140a0c291c-88edc4a3cacb; [bjarne-24c2873fa1e034](https://www.stroustrup.com/examples_short.pdf) / evidence bjarne-24c2873fa1e034-b001854cbc2b; 3 independent supporting works)

- **inferred**: Feature selection. Start with a demonstrated problem and representative applications, then consider a library or tool before adding language machinery. A proposal must fit existing facilities and justify implementation, learning, compatibility and review costs. General mechanisms are valuable, but a merely useful feature can still make the whole language less coherent. These criteria are judgment aids, not a mechanical score. ([bjarne-15c9eb40135f1c](https://www.youtube.com/watch?v=nQPumFkN-Ow&t=1418) / evidence bjarne-15c9eb40135f1c-77677dc4d94b; [bjarne-7e06ae970694d2](https://www.stroustrup.com/how-to-write-a-proposal.pdf) / evidence bjarne-7e06ae970694d2-835d110dd40e; [bjarne-011a23f6854d67](https://www.youtube.com/watch?v=ixmDTTDiEDE&t=1116) / evidence bjarne-011a23f6854d67-3e79244e0098; 3 independent supporting works)

- **inferred**: RAII and invariants. A constructor should establish the conditions needed for valid operations, and a destructor should release owned resources predictably. This applies to locks, sockets and files as well as memory. RAII reduces repeated cleanup paths, but it does not automatically undo external side effects made before a constructor throws; those effects need ordering or explicit rollback. ([bjarne-6d78140a0c291c](https://www.stroustrup.com/bs_faq.html) / evidence bjarne-6d78140a0c291c-b57156585e80; [bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-772d113442fd; [bjarne-259ce62357d855](https://www.stroustrup.com/except89.pdf) / evidence bjarne-259ce62357d855-c25b630f904e; 3 independent supporting works)

- **inferred**: Copying, moving and ownership. An owning class must define or prohibit copying and account for its existing target resources during assignment. Move transfers resources rather than duplicating them; it can support efficient value returns and move-only handles. Prefer unique ownership when ownership is transferred rather than genuinely shared. Shared ownership adds coordination and potentially less predictable destruction; non-owning observers still require valid lifetimes. ([bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-39db093291b9; [bjarne-065773b9938c58](https://www.artima.com/articles/a-brief-introduction-to-rvalue-references) / evidence bjarne-065773b9938c58-6d1307470618; [bjarne-4a995c56f1ad83](https://www.stroustrup.com/what-is-2009.pdf) / evidence bjarne-4a995c56f1ad83-99c767282d51; [bjarne-ebfe802dabed13](https://www.stroustrup.com/resource-model.pdf) / evidence bjarne-ebfe802dabed13-9a5008ccdb01; 4 independent supporting works)

- **documented**: Garbage collection. He did not want mandatory collection in early C++ because of the machines and real-time and driver requirements of the time, but regarded optional collection as useful where affordable. Deterministic release of non-memory resources remains a separate problem. He later supported a C++11 collection interface, then reported its removal after collectors did not use it; that history is not a blanket rejection of collectors. ([bjarne-faf11ea2080fa8](https://www.stroustrup.com/hopl2.pdf) / evidence bjarne-faf11ea2080fa8-2cfebd9f4211; [bjarne-faf11ea2080fa8](https://www.stroustrup.com/hopl2.pdf) / evidence bjarne-faf11ea2080fa8-d4b092795b1f; [bjarne-2ac5f49ea2025b](https://www.youtube.com/watch?v=U46fJ2bJ-co&t=4210) / evidence bjarne-2ac5f49ea2025b-759a98b0cbce; 2 independent supporting works)

- **inferred**: Exception strategy. Use local tests or error values when failure is expected and recovery is nearby; exceptions are useful for uncommon failures that must cross intervening layers. Pair propagation with resource handles and maintained invariants. He later regretted explaining error handling too much as a discussion of exceptions: a legacy system with unmanaged ownership or a constrained runtime may reasonably retain error codes. ([bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-9ef6b6a6ae2d; [bjarne-9e25d165bdd09b](https://www.youtube.com/watch?v=15QF2q66NhU&t=3541) / evidence bjarne-9e25d165bdd09b-bd4a1ce26281; [bjarne-f98c247fbbb5c2](https://www.youtube.com/watch?v=BMtLOKMUHsY&t=3851) / evidence bjarne-f98c247fbbb5c2-25fbe211e3d6; 3 independent supporting works)

- **documented**: Exception guarantees. Aim for valid invariants and no leaks as a basic guarantee; provide unchanged-on-failure behavior where the operation and its costs warrant it; reserve no-throw promises for operations able to support them. Dave Abrahams distilled this framework from library-group work. Guarantees depend on user operations and non-throwing cleanup, and a valid post-failure state is not necessarily the state the application wanted. ([bjarne-5877b33c3b0e61](https://www.stroustrup.com/DnE2005.pdf) / evidence bjarne-5877b33c3b0e61-304b18020433; [bjarne-94f225ac3002e4](https://www.stroustrup.com/except.pdf) / evidence bjarne-94f225ac3002e4-104ff8665678; [bjarne-783c826311cb99](https://www.stroustrup.com/eh_brief.pdf) / evidence bjarne-783c826311cb99-d87cae83a6d3; 3 independent supporting works)

- **inferred**: Hard-real-time constraints. Average speed is insufficient when a deadline requires a credible upper bound. Allocation may depend on history, and exception propagation on the path and destructors executed. Use pools, static storage or other bounded approaches where appropriate, and assess RTTI and toolchain behavior as well. He recommends considering exceptions outside the most stringent cases, not banning them universally. ([bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-0cfbbe01b1d4; [bjarne-36aa60d256697d](https://www.stroustrup.com/abstraction-and-machine.pdf) / evidence bjarne-36aa60d256697d-d6661b025c08; [bjarne-96fe6f0ab0798f](https://www.stroustrup.com/bs_faq2.html) / evidence bjarne-96fe6f0ab0798f-11b98aa0e1b7; 3 independent supporting works)

- **inferred**: Safety profiles. His gradual approach first provides useful abstractions, then restricts hazardous direct operations in code seeking a particular guarantee. Rules, analyzers and libraries must work together; runtime checks remain necessary where static proof is unavailable or too expensive. Profiles and their annotations in the cited proposals are not evidence that all ordinary C++ is safe or that every proposed guarantee is standardized. ([bjarne-15c9eb40135f1c](https://www.youtube.com/watch?v=nQPumFkN-Ow&t=2089) / evidence bjarne-15c9eb40135f1c-04b7a91d5fd0; [bjarne-1b8b2e20ba58f6](https://www.youtube.com/watch?v=41USGJaGsAo&t=536) / evidence bjarne-1b8b2e20ba58f6-2654cb7e9d2a; [bjarne-ba011de2f93d22](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2021/p2410r0.pdf) / evidence bjarne-ba011de2f93d22-5dbe1fe4a278; [bjarne-c470066f9f7b12](https://stroustrup.com/Krill_safety_interview_2023.pdf) / evidence bjarne-c470066f9f7b12-b1e133b328f3; 4 independent supporting works)

- **inferred**: Bounds and spans. A span carries an extent that a bare pointer does not, making range-aware interfaces possible. That information does not prove that a caller supplied a correct pointer and length, and standard span alone does not guarantee checking in the cited 2025 account. Use enforcement or a hardened implementation where required, and review unverified foreign or hardware boundaries explicitly. ([bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-880a67a8640c; [bjarne-e6ea9034480210](https://www.youtube.com/watch?v=iu2A3qVkLQY&t=2638) / evidence bjarne-e6ea9034480210-43484886fffa; [bjarne-ba011de2f93d22](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2021/p2410r0.pdf) / evidence bjarne-ba011de2f93d22-2b39cee4798f; 3 independent supporting works)

- **inferred**: Lifetime analysis. Ownership is only part of pointer safety: references, iterators, captures and other aliases can outlive an object or be invalidated by container mutation. His local-analysis proposals conservatively treat potentially invalidating calls as invalidating and use checked annotations to recover precision. This can reject safe code; suppression is a trust boundary, not proof that the suppressed operation is safe. ([bjarne-ebfe802dabed13](https://www.stroustrup.com/resource-model.pdf) / evidence bjarne-ebfe802dabed13-a370b6b0fc6a; [bjarne-932ad8b20d3133](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4418r0.pdf) / evidence bjarne-932ad8b20d3133-5160944aacd6; [bjarne-1b8b2e20ba58f6](https://www.youtube.com/watch?v=41USGJaGsAo&t=2883) / evidence bjarne-1b8b2e20ba58f6-b479d5491e6a; 3 independent supporting works)

- **inferred**: Initialization. Initialize ordinary objects at definition so their validity is locally visible. Do not turn that rule into a requirement to initialize all raw storage immediately: pools, vector implementations and large communication buffers may intentionally defer construction or overwrite storage. Such exceptions need explicit discipline and checks that each object is initialized before use on every relevant path. ([bjarne-4e11090450bc3d](https://www.youtube.com/watch?v=2BuJjaGuInI&t=1541) / evidence bjarne-4e11090450bc3d-49df41321e2e; [bjarne-1b8b2e20ba58f6](https://www.youtube.com/watch?v=41USGJaGsAo&t=982) / evidence bjarne-1b8b2e20ba58f6-c8448c7dfb61; [bjarne-1b8b2e20ba58f6](https://www.youtube.com/watch?v=41USGJaGsAo&t=1497) / evidence bjarne-1b8b2e20ba58f6-94ea94795c58; 2 independent supporting works)

- **documented**: Generic programming and concepts: changed views. In the 1988 template proposal and a historical paper with Andrew Koenig, explicit constraints as then conceived risked excessive restriction or complexity. Later, Stroustrup pursued concepts to express usable interfaces and improve diagnostics and overload selection. Concepts were not included in C++11; C++20 supplied a later design. Historical proposals and their syntax must not be mistaken for the final standard. ([bjarne-b1a888823a69fd](https://www.stroustrup.com/parameterized_types_1988.pdf) / evidence bjarne-b1a888823a69fd-160df6185bcf; [bjarne-3d5d545f1e6ccf](https://www.stroustrup.com/style95.pdf) / evidence bjarne-3d5d545f1e6ccf-470682c55eb5; [bjarne-0fb2730c7ce8f5](https://www.stroustrup.com/OpenPatternMatching.pdf) / evidence bjarne-0fb2730c7ce8f5-2aea6047a6ef; [bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-6e2e0a4876f2; 4 independent supporting works)

- **inferred**: Concept semantics and completeness. Prefer reusable concepts representing meaningful domain ideas over a collection of unrelated operation checks. A compiler can check syntax, but not generally prove semantic laws: floating-point NaNs, for example, complicate ordering assumptions. His later view also accepts incomplete concepts during migration or development because partial checking can catch errors early, while missing requirements may still fail at instantiation. ([bjarne-72241b845beaaf](https://www.stroustrup.com/sle2011-concepts.pdf) / evidence bjarne-72241b845beaaf-e69f8cfa27fe; [bjarne-b23c7274491b67](https://www.stroustrup.com/good_concepts.pdf) / evidence bjarne-b23c7274491b67-35649ba498f3; [bjarne-e6ea9034480210](https://www.youtube.com/watch?v=iu2A3qVkLQY&t=5498) / evidence bjarne-e6ea9034480210-b909c060f325; 3 independent supporting works)

- **documented**: Checking template definitions: revised view. In 2005 he described complete checking of a template in isolation as an aim. Later he concluded that checking the interface at use sites supplies much of the benefit, while strict definition checking can obstruct implementation scaffolding such as logging. He remains open to better definition checking if those practical problems can be handled. ([bjarne-5877b33c3b0e61](https://www.stroustrup.com/DnE2005.pdf) / evidence bjarne-5877b33c3b0e61-1007c6f77705; [bjarne-b23c7274491b67](https://www.stroustrup.com/good_concepts.pdf) / evidence bjarne-b23c7274491b67-3e64cafb8385; [bjarne-a6e6b66c93ddae](https://www.youtube.com/watch?v=hVoJgOwLNbE&t=6655) / evidence bjarne-a6e6b66c93ddae-010b980295d1; 3 independent supporting works)

- **inferred**: Static and dynamic polymorphism. Templates fit operations and types known at compile time, whereas virtual interfaces fit implementations selected at runtime. Combine them when a problem needs both, such as a generic container of polymorphic shapes. Neither style is automatically faster or more maintainable in every workload; unnecessary hierarchy and brittle metaprogramming are both failure modes. ([bjarne-8499a11781ef93](https://www.stroustrup.com/Concept-based-GP.pdf) / evidence bjarne-8499a11781ef93-470b9c90ee91; [bjarne-a6e6b66c93ddae](https://www.youtube.com/watch?v=hVoJgOwLNbE&t=1067) / evidence bjarne-a6e6b66c93ddae-869754e54d34; [bjarne-032faa90b6e56c](https://www.stroustrup.com/hopl-almost-final.pdf) / evidence bjarne-032faa90b6e56c-60151408f37f; 3 independent supporting works)

- **inferred**: Containers and algorithms. Separate algorithms from storage through iterator or range interfaces so one algorithm can serve multiple structures. Contiguous storage is a useful default because traversal and cache behavior matter, but it is not a universal winner. Consider element size, copying, allocation, mutation and the complete workload; list operations can be preferable in cases where their actual access pattern fits. ([bjarne-5877b33c3b0e61](https://www.stroustrup.com/DnE2005.pdf) / evidence bjarne-5877b33c3b0e61-2a58ed4f16ea; [bjarne-c9839d4ff3a827](https://isocpp.org/blog/2014/06/stroustrup-lists) / evidence bjarne-c9839d4ff3a827-fc50f5b4249b; [bjarne-c9839d4ff3a827](https://isocpp.org/blog/2014/06/stroustrup-lists) / evidence bjarne-c9839d4ff3a827-a5da1e6ae3f9; 2 independent supporting works)

- **inferred**: Measurement and optimization. Start with clear code and a suitable data model, then measure the constraint that matters: runtime, memory, code size, startup or another resource. Optimize the actual bottleneck rather than assuming an abstraction or allocation is costly. His suggestion that special optimization might concern roughly 2–3% of code is a heuristic, not a universal threshold. ([bjarne-2ac5f49ea2025b](https://www.youtube.com/watch?v=U46fJ2bJ-co&t=5278) / evidence bjarne-2ac5f49ea2025b-ec92dd7ba670; [bjarne-4e11090450bc3d](https://www.youtube.com/watch?v=2BuJjaGuInI&t=975) / evidence bjarne-4e11090450bc3d-a5f2f647c475; [bjarne-3814e2c99fbc0c](https://www.stroustrup.com/21st-Century-C++.pdf) / evidence bjarne-3814e2c99fbc0c-d9e1d664c7a7; 3 independent supporting works)

- **inferred**: Modules and headers. C++20 modules address repeated textual inclusion, order dependence and leakage across headers. Compilation gains can be substantial in particular examples, but migration requires organization changes, toolchain support and attention to macros. His measured hello-world improvement is not a general forecast. Header and module interfaces may coexist during a long transition. ([bjarne-011a23f6854d67](https://www.youtube.com/watch?v=ixmDTTDiEDE&t=2417) / evidence bjarne-011a23f6854d67-b0aae142e454; [bjarne-011a23f6854d67](https://www.youtube.com/watch?v=ixmDTTDiEDE&t=2595) / evidence bjarne-011a23f6854d67-96410bc4f10e; [bjarne-a6e6b66c93ddae](https://www.youtube.com/watch?v=hVoJgOwLNbE&t=7670) / evidence bjarne-a6e6b66c93ddae-538f75a24573; 2 independent supporting works)

- **inferred**: Compile-time computation. With Gabriel Dos Reis, he pursued typed constexpr functions as a clearer way to compute values than macros or elaborate template metaprograms. C++11 began with deliberately limited support, later expanded in C++14 and subsequent standards. Compile-time work can improve safety and eliminate runtime work, but it consumes compiler resources and is not desirable for every computation. ([bjarne-189b97e60bf82d](https://www.youtube.com/watch?v=ZO0PXYMVGSU&t=5170) / evidence bjarne-189b97e60bf82d-835b7457dff2; [bjarne-011a23f6854d67](https://www.youtube.com/watch?v=ixmDTTDiEDE&t=3704) / evidence bjarne-011a23f6854d67-90c19eb1d4b0; [bjarne-e6ea9034480210](https://www.youtube.com/watch?v=iu2A3qVkLQY&t=4664) / evidence bjarne-e6ea9034480210-d68f5685f679; 3 independent supporting works)

- **inferred**: Concurrency. Systems support needs low-level primitives and a memory model, but ordinary application code should use higher-level mechanisms when they fit. Locks can create deadlock, livelock and priority-inversion risks; lock-free techniques require specialist reasoning about progress, atomicity and reclamation. A concurrent interface must also make compound operations meaningful, not merely make each sequential operation individually thread-safe. ([bjarne-4a995c56f1ad83](https://www.stroustrup.com/what-is-2009.pdf) / evidence bjarne-4a995c56f1ad83-cd9a87462438; [bjarne-42c5d271888cb3](https://www.stroustrup.com/smc_it2009.pdf) / evidence bjarne-42c5d271888cb3-6176857389a4; [bjarne-42c5d271888cb3](https://www.stroustrup.com/smc_it2009.pdf) / evidence bjarne-42c5d271888cb3-e8b314622dba; [bjarne-4a995c56f1ad83](https://www.stroustrup.com/what-is-2009.pdf) / evidence bjarne-4a995c56f1ad83-1b5060d2d712; 2 independent supporting works)

- **inferred**: Teaching. Teach useful abstractions and programming techniques alongside language features, then use familiar implementations to explain lower-level machinery. Strings and vectors let beginners solve meaningful problems without first writing manual buffer management. This is not a universal curriculum: learner goals, available libraries and the need for systems knowledge change the sequence. He explicitly limits his claimed expertise about teaching younger children. ([bjarne-f8c2555fc934a2](https://www.stroustrup.com/new_learning.pdf) / evidence bjarne-f8c2555fc934a2-c07deddb68ea; [bjarne-f8c2555fc934a2](https://www.stroustrup.com/new_learning.pdf) / evidence bjarne-f8c2555fc934a2-71b0bf92e762; [bjarne-15c9eb40135f1c](https://www.youtube.com/watch?v=nQPumFkN-Ow&t=2561) / evidence bjarne-15c9eb40135f1c-8dbfba7809ec; [bjarne-7cfc6df3edd752](https://cacm.acm.org/opinion/what-should-we-teach-new-software-developers-why/) / evidence bjarne-7cfc6df3edd752-2df22de02022; 3 independent supporting works)

- **documented**: Readability and deduction. He advocated auto to remove burdensome type repetition, but later observed that excessive deduction can hide the type or requirement a reader needs. Use a named concept or explicit type when it communicates the interface better. Compact writing is not the goal by itself: code has to remain understandable to maintainers. ([bjarne-4a995c56f1ad83](https://www.stroustrup.com/what-is-2009.pdf) / evidence bjarne-4a995c56f1ad83-7844ff3ddfd4; [bjarne-2ac5f49ea2025b](https://www.youtube.com/watch?v=U46fJ2bJ-co&t=3804) / evidence bjarne-2ac5f49ea2025b-6fe3a2b4806b; [bjarne-189b97e60bf82d](https://www.youtube.com/watch?v=ZO0PXYMVGSU&t=4394) / evidence bjarne-189b97e60bf82d-77bf8d39f571; 3 independent supporting works)
