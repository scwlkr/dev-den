# Dennis M. Ritchie: principles

Built from 31 accepted distinct works and 138,939 source words. Compiled reasoning with source support and limits below.

- **inferred**: Prefer a compact interface that covers a useful range of real work, not compactness for its own sake. Test it with ordinary applications and look for the tasks it excludes. Unix's small design was shaped by resource constraints and use, but Ritchie acknowledged missing synchronization and cases needing asynchronous I/O.  Application: keep a proposed generalization out until its practical benefit and fit are clear, while recording unmet needs rather than declaring them impossible or unimportant. - **inferred**: Treat uniform interfaces as leverage, not proof of identical underlying behavior. Reusing file naming and I/O can make devices and services usable by existing programs, but read-ahead, device semantics and machine-specific data can still break expectations.  Application: specify the shared contract, then test boundary cases such as sequential consumers, remote debugging and access control rather than assuming that a common API makes every resource interchangeable. - **inferred**: Keep data output distinct from diagnostics and avoid compulsory interaction when a program is intended for composition. Extra explanatory output can change the meaning of a downstream count; a prompt can stop unattended processing.  The qualification matters: Ritchie allowed that some tables benefit from headings. Application: make the machine-consumed stream predictable, put errors on a separate channel, and provide explicit human-oriented modes where useful. - **inferred**: Distinguish portable source, portable interfaces and portable data. A common interface can have machine-specific implementations; source can compile on both machines while a binary file still carries byte-order assumptions.  Application: write separate tests for language assumptions, the operating-system boundary and persistent or transmitted representations. - **inferred**: Keep target-dependent work explicit rather than promising that abstraction removes it. Isolating primitives helps contain change, but bringing up a compiler and operating system still requires knowledge of representations, interrupts, memory and devices.  The two works are closely related, so they should not be mistaken for independent replications. Application: fund target expertise and integration testing even when most code is shared. - **inferred**: Measure performance in the context of the workload, implementation and other resources consumed. - **inferred**: Accept a higher-level implementation cost when it buys enough clarity and changeability, but optimize the hot parts and disclose what else changed.  The Unix rewrite's larger size cannot be attributed solely to C because it also added capabilities. Ritchie's object-size estimates were guesses. Application: compare development and maintenance benefits alongside measured speed and memory, and retain machine-specific code where the evidence justifies it. - **inferred**: Evaluate language features against actual systems work, implementation technology and the surrounding environment. Elegance or formal definition alone does not ensure adoption; users need an understandable language, an available implementation and useful interaction with their systems.  Ritchie explicitly refrained from claiming a definitive explanation of C's success. Application: prototype the compiler and real interfaces early, and distinguish a technically portable language from an ecosystem people can use. Application: remove or delay an unsound mechanism rather than accepting it because the problem is real, and test old and new code together before recommending a migration path. - **inferred**: Make the implementation and operational limits visible in the design. Streams avoided copies by passing blocks, but consumers had to reconstruct records across arbitrary boundaries. A user-mode simulator eased development, but lacked some hardware support and was not intended for production.  Application: list what the abstraction moves onto its users, including partial messages, recovery, missing devices and debugging costs; do not describe those burdens as implementation trivia. - **documented**: Use the system being designed and keep its source easy to revise. Thompson and Ritchie argued that direct use reveals functional and superficial deficiencies and creates motivation to fix them.  Application: make designers perform representative tasks and give them a path to repair recurring friction. - **inferred**: Account for safety at the actual boundary, not only in the nominal permission model.
