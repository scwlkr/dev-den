# Dennis M. Ritchie: positions

Built from 30 accepted distinct works and 129,100 source words. Compiled reasoning with source support and limits below.

- **documented**: C as a systems language. C was built to express the systems programs the team needed, not primarily to teach programming or enforce restrictions. Its operations are close enough to machine capabilities to support efficient implementations, yet sufficiently abstract for portable programs. This is a balance, not a safety guarantee: Ritchie accepted that objections to C array safety have merit. The 1978 language paper characterizes C collectively; the later assessments are his own. - **inferred**: Portability has layers. In 1978 Johnson and Ritchie distinguished source portability from transferring encoded data: PDP-11 and Interdata byte order could require conversion of a filesystem image even when the source code was portable. Their proposed port also isolated machine-specific kernel and compiler code, but did not eliminate the expertise needed for interrupts, memory management, devices, or calling conventions. Treat application source, persistent formats, operating-system interfaces, and the compiler as separate portability questions. ([ritchie-be88b7b72521cb](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/portpap.html) / evidence ritchie-be88b7b72521cb-49e2f4e6e593; [ritchie-be88b7b72521cb](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/portpap.html) / evidence ritchie-be88b7b72521cb-ca6d166a6742; [ritchie-8aefaea5632426](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/firstport.html) / evidence ritchie-8aefaea5632426-beb6a3967ae4; 2 independent supporting works)

- **inferred**: Port the environment when it is the obstacle. Ritchie recalled that adapting Unix tools to other operating systems was harder than accommodating new hardware. The 1978 Johnson–Ritchie account therefore describes moving Unix itself, not merely individual programs. This avoided some interface mismatches but deliberately did not promise compatibility with all existing target software and formats. It is a strong choice when controlling the destination environment is feasible, not a universal substitute for interoperability. ([ritchie-c6c3e1227aedef](https://ftpmirror2.infania.net/sites/unixarchive/Documentation/OralHistory/transcripts/ritchie.htm) / evidence ritchie-c6c3e1227aedef-c67f13be88be; [ritchie-be88b7b72521cb](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/portpap.html) / evidence ritchie-be88b7b72521cb-ed5c5dc9c4f4; [ritchie-be88b7b72521cb](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/portpap.html) / evidence ritchie-be88b7b72521cb-e0a32e7cfa46; [ritchie-be88b7b72521cb](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/portpap.html) / evidence ritchie-be88b7b72521cb-0a5cb5376f68; 2 independent supporting works)

- **inferred**: Pointer and integer assumptions. Early C and Unix code often treated pointers and integers as similarly represented and treated pointers to different object sizes as interchangeable. The portability project identified machines where those assumptions failed; later C evolution added unsigned types and more explicit conversions while discouraging integer-pointer assignments. Historical PDP-11 permissions are not advice to rely on those conversions in modern C. Audit representation, alignment, and function interfaces rather than assuming a cast makes a representation portable. ([ritchie-8aefaea5632426](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/firstport.html) / evidence ritchie-8aefaea5632426-a9d0a8393e52; [ritchie-8aefaea5632426](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/firstport.html) / evidence ritchie-8aefaea5632426-f8ec95609c17; [ritchie-91fa14fdc827e6](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html) / evidence ritchie-91fa14fdc827e6-9518f1758b1e; [ritchie-50a70b87adf27f](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/cman.pdf) / evidence ritchie-50a70b87adf27f-bde0a203fcf3; 3 independent supporting works)

- **documented**: Function prototypes and migration. Ritchie later regarded missing argument types in function signatures as a significant early design mistake, partly caused by his avoidance of separate-compilation checking and incomplete understanding of typing. In 1989 he supported prototypes but warned about errors when old and new declarations coexist. By his 1993 history he called the committee's compatibility compromise as good as feasible, while acknowledging the resulting complexity and old compiler support burden. ([ritchie-91fa14fdc827e6](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html) / evidence ritchie-91fa14fdc827e6-18f89eebbfe2; [ritchie-56c00e367e631d](https://www.stroustrup.com/From-C-to-Cpp-dmr.pdf) / evidence ritchie-56c00e367e631d-cc2ca5ccb053; [ritchie-91fa14fdc827e6](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html) / evidence ritchie-91fa14fdc827e6-bbb0a9f24a36; [ritchie-65e5badd1cd1d9](https://www.ibiblio.org/pub/linux/docs/linux-doc-project/linuxfocus/English/July1999/article79.html) / evidence ritchie-65e5badd1cd1d9-b6f40ac3227d; 3 independent supporting works)

- **inferred**: Unspecified evaluation order. The historical C manual leaves ordinary expression evaluation order open while specifying order for particular logical operators. Johnson and Ritchie's 1981 calling-sequence paper explains why stricter argument order could impose costs or compiler complexity on different stack designs. The practical implication is to separate side effects when correctness depends on order; the historical rationale does not make every side-effect combination valid under modern C. ([ritchie-50a70b87adf27f](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/cman.pdf) / evidence ritchie-50a70b87adf27f-24a1124aa374; [ritchie-5d25d1308143eb](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/clcs.html) / evidence ritchie-5d25d1308143eb-d675acef5093; [ritchie-50a70b87adf27f](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/cman.pdf) / evidence ritchie-50a70b87adf27f-ddac0747fbd7; 2 independent supporting works)

- **inferred**: Aliasing and optimization. Ritchie acknowledged that pointer overlap obstructs optimization, especially for numerical work on vector machines. In his 1989 interview he opposed a proposed no-alias facility because he judged its rules incorrect, not because the underlying problem was imaginary. In 2000 he identified restricted pointers as a useful C99 addition while otherwise expressing reservations about growth. A real optimization need does not justify a specification whose guarantees cannot be stated correctly. ([ritchie-56c00e367e631d](https://www.stroustrup.com/From-C-to-Cpp-dmr.pdf) / evidence ritchie-56c00e367e631d-c695af655ac1; [ritchie-91fa14fdc827e6](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html) / evidence ritchie-91fa14fdc827e6-6d90f6ed835c; [ritchie-4cf698ce0647a8](https://www.computerworld.com/article/1605643/the-future-according-to-dennis-ritchie-a-2000-interview.html) / evidence ritchie-4cf698ce0647a8-541dde5ed009; 3 independent supporting works)

- **inferred**: Const is not a universal no-change promise. In 1989 Ritchie distinguished restricting writes through a pointer from proving that the referenced object cannot change through some other route. He accepted the qualifier's usefulness for read-only storage but warned against treating it as a stronger aliasing or optimization guarantee. When designing an interface, state separately who may write, which aliases can exist, and what the optimizer may assume. ([ritchie-56c00e367e631d](https://www.stroustrup.com/From-C-to-Cpp-dmr.pdf) / evidence ritchie-56c00e367e631d-c0fb38435c90; [ritchie-91fa14fdc827e6](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html) / evidence ritchie-91fa14fdc827e6-6d90f6ed835c; 2 independent supporting works)

- **inferred**: Arrays, pointers, and strings. Ritchie's account explains array-to-pointer conversion as a way to preserve much B code while enabling structures; the historical manual derives subscripting from pointer arithmetic. His 1993 assessment says character arrays and a terminator simplify C's language rules, but make some operations scan for the end and leave storage management to users. Do not equate an array object with a pointer in every modern C context: the old manual is not a complete modern specification. ([ritchie-91fa14fdc827e6](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html) / evidence ritchie-91fa14fdc827e6-5c5b9dd1158f; [ritchie-50a70b87adf27f](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/cman.pdf) / evidence ritchie-50a70b87adf27f-4bea9c72626f; [ritchie-91fa14fdc827e6](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html) / evidence ritchie-91fa14fdc827e6-481181022e03; [ritchie-91fa14fdc827e6](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html) / evidence ritchie-91fa14fdc827e6-394d27ee788a; 2 independent supporting works)

- **documented**: Runtime-sized multidimensional arrays. In 1990 Ritchie identified awkward numerical-library interfaces as a real gap. His proposal carried adjustable bounds in pointers, preserving the relationship between pointer type, value, dereference, and arithmetic; conversions had to supply those bounds. He acknowledged the storage and syntax costs, including inconvenient explicit dereferencing. This was a proposal with a compatibility goal, not evidence that C99 adopted his particular fat-pointer design. ([ritchie-b899843558a2e0](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/vararray.html) / evidence ritchie-b899843558a2e0-b377e0e0f157; [ritchie-b899843558a2e0](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/vararray.html) / evidence ritchie-b899843558a2e0-145ac8d24205; [ritchie-b899843558a2e0](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/vararray.html) / evidence ritchie-b899843558a2e0-6dbd460b1565; [ritchie-b899843558a2e0](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/vararray.html) / evidence ritchie-b899843558a2e0-f7cd6fe63b4b; 1 independent supporting works)

- **inferred**: Declaration syntax. C declarators were designed by analogy with expressions that use the declared object. In 1993 Ritchie defended this as a plausible unifying principle while acknowledging difficult inside-out forms. In the later interview published with a 1999 copyright, he remained uncertain and recognized criticism of the syntax. Use the analogy to explain declarations, but do not mistake a coherent design rationale for proof that every complex declarator is easy to read. ([ritchie-91fa14fdc827e6](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html) / evidence ritchie-91fa14fdc827e6-7cc95771d1b3; [ritchie-91fa14fdc827e6](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html) / evidence ritchie-91fa14fdc827e6-afda41a8616a; [ritchie-65e5badd1cd1d9](https://www.ibiblio.org/pub/linux/docs/linux-doc-project/linuxfocus/English/July1999/article79.html) / evidence ritchie-65e5badd1cd1d9-09982e3defb0; 2 independent supporting works)

- **documented**: C standardization and language growth. Ritchie valued standards for public review and a basis for challenging nonconforming implementations, but worried that broad participation could erode a language's unity; he also warned against extreme early control. In 2000 he preferred the compactness of the 1989/1990 standard to C99, while accepting that C had to evolve and recognizing the need to address 64-bit issues. He had not participated in C99 work. ([ritchie-4cf698ce0647a8](https://www.computerworld.com/article/1605643/the-future-according-to-dennis-ritchie-a-2000-interview.html) / evidence ritchie-4cf698ce0647a8-7674e7ad909f; [ritchie-4cf698ce0647a8](https://www.computerworld.com/article/1605643/the-future-according-to-dennis-ritchie-a-2000-interview.html) / evidence ritchie-4cf698ce0647a8-541dde5ed009; 1 independent supporting works)

- **inferred**: Libraries are part of portability. C does not itself define external interaction, so Ritchie considered a careful standard library essential. He recalled that the original standard I/O interface took several attempts because it needed to work on operating systems without Unix-like read and write. The lesson is to specify the useful application-level contract independently of one operating system's primitives, while allowing implementations to adapt underneath. ([ritchie-91fa14fdc827e6](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html) / evidence ritchie-91fa14fdc827e6-8d93c66ba920; [ritchie-56c00e367e631d](https://www.stroustrup.com/From-C-to-Cpp-dmr.pdf) / evidence ritchie-56c00e367e631d-f1675eadbb13; 2 independent supporting works)

- **documented**: Byte streams and composition. The 1978 Unix paper by Ritchie and Thompson places ordinary file structure in the programs using the file, rather than in the kernel. Ritchie's 1977 retrospective adds that a common text representation helps independently written tools interoperate, while applications may still impose records above the interface. This is an argument for a shared lowest-level contract, not a prohibition on structured data or formats. ([ritchie-4495b38593615b](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/cacm.html) / evidence ritchie-4495b38593615b-0db7c2c23d73; [ritchie-504320fb4a7e46](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/retro.html) / evidence ritchie-504320fb4a7e46-583a37c2b61f; [ritchie-f9fdc2ceaea02e](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/notes.html) / evidence ritchie-f9fdc2ceaea02e-f1b56987b0aa; 3 independent supporting works)

- **documented**: Devices as files. Ritchie and Thompson describe common device and file naming, I/O, and protection as three benefits of special files. Ritchie tentatively recalled contributing the device-file idea, while crediting most of the early filesystem design to Thompson. Uniformity is an aspiration with limits: later file-oriented designs still distinguish dynamic device behavior, and access to sensitive devices requires protection. ([ritchie-4495b38593615b](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/cacm.html) / evidence ritchie-4495b38593615b-1d7ab0b69aef; [ritchie-7ca8eec9ac8af9](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/hist.html) / evidence ritchie-7ca8eec9ac8af9-9e97afe4d556; [ritchie-f9fdc2ceaea02e](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/notes.html) / evidence ritchie-f9fdc2ceaea02e-7a128b941bc4; 3 independent supporting works)

- **documented**: Pipelines and command design. The Unix pipeline's distinctive advantage, in Ritchie's 1979 account, is that ordinary commands can also be connected without being rewritten as special stream modules. The shell handles redirection, allowing commands to rely on standard descriptors; separate diagnostics help preserve data output. The linear notation is not a complete answer for multiple inputs and outputs, and finite buffers can make more general graphs difficult. ([ritchie-7ca8eec9ac8af9](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/hist.html) / evidence ritchie-7ca8eec9ac8af9-d728fd6527c4; [ritchie-4495b38593615b](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/cacm.html) / evidence ritchie-4495b38593615b-39f880ab09d2; [ritchie-7ca8eec9ac8af9](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/hist.html) / evidence ritchie-7ca8eec9ac8af9-0c8d8f666b4d; [ritchie-504320fb4a7e46](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/retro.html) / evidence ritchie-504320fb4a7e46-ac37ba2fc657; 3 independent supporting works)

- **inferred**: Centralized shell policy has edges. Ritchie favored shell-managed redirection and filename expansion because code appears once and behavior is uniform across commands. His counterexample is restoration: expanding a wildcard against files currently present cannot generally select saved files that are absent locally. Put policy in a common layer when that layer has the information needed; let a specialized command interpret the request when it does not. ([ritchie-504320fb4a7e46](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/retro.html) / evidence ritchie-504320fb4a7e46-25ac5d9813cf; [ritchie-4495b38593615b](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/cacm.html) / evidence ritchie-4495b38593615b-737861fe68ed; 2 independent supporting works)

- **documented**: Minimal interfaces and missing primitives. In the 1977 retrospective Ritchie preferred implementing mechanisms with existing primitives, adding an interface when serious, demonstrable inefficiency justified it. He nevertheless called the absence of general interprocess synchronization a weakness in some uses and identified applications needing genuinely asynchronous I/O. His later interview also admitted that features omitted because the team did not need or understand them could leave general weaknesses. ([ritchie-504320fb4a7e46](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/retro.html) / evidence ritchie-504320fb4a7e46-efadf4f35931; [ritchie-504320fb4a7e46](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/retro.html) / evidence ritchie-504320fb4a7e46-8a9c03798f09; [ritchie-c6c3e1227aedef](https://ftpmirror2.infania.net/sites/unixarchive/Documentation/OralHistory/transcripts/ritchie.htm) / evidence ritchie-c6c3e1227aedef-0f75bf673e1d; 2 independent supporting works)

- **documented**: File locking is workload-dependent. In the 1978 Unix paper Ritchie and Thompson rejected user-visible file locks as neither necessary nor sufficient in their environment: they did not have large shared databases, and a lock could not prevent every conflict involving editors that work on copies. They retained internal interlocks for filesystem consistency and acknowledged that simultaneous writes could scramble contents. This does not establish that locks are unnecessary for database or collaborative workloads. ([ritchie-4495b38593615b](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/cacm.html) / evidence ritchie-4495b38593615b-3b931cb731a0; 1 independent supporting works)

- **documented**: Distributed resources and namespaces. In the 1999 Styx paper Pike and Ritchie present resources as files in hierarchical namespaces, using one protocol for local and remote access. Inferno's coauthored account adds private namespaces and controlled mounting; the 2000 interview describes private process-group namespaces in Plan 9. The benefit is a common access model, not an assertion that networks are reliable or that every resource behaves like an ordinary disk file. ([ritchie-032d8ab9a984c0](https://inferno-os.org/inferno/papers/styx.html) / evidence ritchie-032d8ab9a984c0-6022d3c10326; [ritchie-032d8ab9a984c0](https://inferno-os.org/inferno/papers/styx.html) / evidence ritchie-032d8ab9a984c0-31d8a3ce023c; [ritchie-53a93514dbf681](https://www.inferno-os.org/inferno/papers/bltj.html) / evidence ritchie-53a93514dbf681-e4e6209ef64a; [ritchie-4cf698ce0647a8](https://www.computerworld.com/article/1605643/the-future-according-to-dennis-ritchie-a-2000-interview.html) / evidence ritchie-4cf698ce0647a8-f0e92c38f62e; 3 independent supporting works)

- **inferred**: Security requires the operating conditions. In 1977 Ritchie distinguished a theoretically adequate permission model from practical failures involving defaults, privileged programs, raw-disk access, and denial of service. The 1999 Styx paper adds authenticated identity and optional channel protection; the Inferno paper describes limiting application resources through the namespace. These are complementary controls, not proof that a file abstraction or a permission bit alone makes a system secure. ([ritchie-504320fb4a7e46](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/retro.html) / evidence ritchie-504320fb4a7e46-b4d77bdd26bf; [ritchie-032d8ab9a984c0](https://inferno-os.org/inferno/papers/styx.html) / evidence ritchie-032d8ab9a984c0-d098bc84d03f; [ritchie-53a93514dbf681](https://www.inferno-os.org/inferno/papers/bltj.html) / evidence ritchie-53a93514dbf681-ef40bb86f774; 3 independent supporting works)

- **documented**: Streams and protocol composition. Ritchie's 1984 streams paper replaces a rigid character-I/O organization with modules connected by narrow message interfaces. Passing references to blocks avoids copying and amortizes overhead, but each module must handle arbitrary chunk boundaries. He rejected a process per module because supporting around 1,000 queues appeared too costly in storage; explicit saved state was the accepted loss in elegance. The design does not itself solve general multiplexing. ([ritchie-5cfbec4274be6e](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/st.html) / evidence ritchie-5cfbec4274be6e-6a82f9b9fc75; [ritchie-5cfbec4274be6e](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/st.html) / evidence ritchie-5cfbec4274be6e-7cba78c0a380; [ritchie-5cfbec4274be6e](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/st.html) / evidence ritchie-5cfbec4274be6e-24812916f8e7; [ritchie-5cfbec4274be6e](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/st.html) / evidence ritchie-5cfbec4274be6e-2cced736db5e; [ritchie-5cfbec4274be6e](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/st.html) / evidence ritchie-5cfbec4274be6e-a1ac6d4c436e; 1 independent supporting works)

- **inferred**: Message passing has operational costs. In the 1984 streams implementation, locking a stream until an I/O-control reply avoided reply matching, but a late reply could cause a false error and a lost reply a long wait. Anonymous server execution also obscured caller identity, complicated privileged operations, and weakened accounting. Interface regularity must be evaluated alongside timeout behavior, attribution, and observability. ([ritchie-5cfbec4274be6e](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/st.html) / evidence ritchie-5cfbec4274be6e-63e42585cbac; [ritchie-5cfbec4274be6e](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/st.html) / evidence ritchie-5cfbec4274be6e-01b4dfe6e43c; 1 independent supporting works)

- **inferred**: Higher-level implementation versus cost. Ritchie and Thompson's 1978 paper reports that the C Unix rewrite was about one-third larger than the earlier assembly system, but also easier to understand and modify and more capable. Ritchie's separate retrospective estimated typical C object inflation at 20–40 percent and similar speed costs, explicitly as guesses rather than a comprehensive study. Profile the hot path before trading maintainability for assembly; do not treat the historical percentages as current benchmarks. ([ritchie-4495b38593615b](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/cacm.html) / evidence ritchie-4495b38593615b-06ce23761ef4; [ritchie-504320fb4a7e46](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/retro.html) / evidence ritchie-504320fb4a7e46-e3a7f531ddae; [ritchie-be88b7b72521cb](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/portpap.html) / evidence ritchie-be88b7b72521cb-4eaf89778fa3; 3 independent supporting works)

- **inferred**: Performance measurements need a workload. In the 1977 retrospective Ritchie considered larger disk blocks potentially faster for a copy test, but noted approximately 15 percent more occupied space on his machine and possible cache effects; the idle-machine experiment was not statistically general. His 1984 streams results likewise differed for direct and network terminals, and he warned that proper comparable measurements had not been made. Do not select a design from one favorable throughput figure. ([ritchie-504320fb4a7e46](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/retro.html) / evidence ritchie-504320fb4a7e46-b879833d643e; [ritchie-5cfbec4274be6e](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/st.html) / evidence ritchie-5cfbec4274be6e-6d82eac160f0; 2 independent supporting works)

- **documented**: Compiler retargetability is not automatic. The 1978 Johnson–Ritchie portability paper describes separating machine facts from code-generation strategy, and credits Johnson with undertaking the portable compiler. It also favors rejecting input when the compiler detects its own inability to generate correct code. Retargeting still requires expertise in representation, runtime conventions, and instruction selection; the earlier proposal explicitly rejected an interpreter bootstrap as the intended route to efficient generated code. - **inferred**: Calling conventions must survive interrupts and debugging. Johnson and Ritchie's 1981 report requires stack and environment registers to be valid at interruptible points, and recommends working out an unwinding algorithm before committing to a frame layout. It also explains why caller-owned result space can preserve reentrancy for returned structures, while acknowledging that the PDP-11 implementation used static storage instead. A fast call sequence that cannot be unwound or interrupted correctly is incomplete. - **documented**: Register arguments changed with the machines. In 1981 Johnson and Ritchie judged passing initial arguments in registers tempting but not yet practical in their experience, given architectural constraints. A 2003 note on the coauthored report says it became practical shortly afterward; its individual author is unidentified. Preserve both observations: an implementation assessment can be correct for its period without becoming a permanent language-design rule. - **inferred**: Reliability and real time are separate dimensions. Ritchie distinguished fast kernel collection of terminal input from scheduling a user program quickly enough to respond; his 1972 notes describe limitations tied to swapping. His 1977 retrospective separately discusses uptime, file preservation, and correctness, warning that crash recovery was not automatic and backups mattered. A system suitable for interactive development is not thereby a hard real-time or fault-tolerant system. - **inferred**: Implementation and adoption matter to language design. In his 1993 talk Ritchie argued that apparently elegant, orthogonal language features can expose unexpected implementation difficulties, and that users need understandable definitions and available compilers that work on contemporary machines. In the 2000 interview he also warned that successful adoption makes early mistakes harder to fix. Test both implementation and migration paths before declaring a language design complete.
