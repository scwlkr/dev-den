- **documented**: Clean Architecture: Identify domain entities, application-specific use cases, interface adapters, and external mechanisms. An interactor orchestrates entities; controllers translate incoming data, while presenters translate results for display. Source dependencies cross boundaries toward policy, even when control flows outward through an interface. Use this when business rules need fast tests or protection from infrastructure changes. The four circles are illustrative, not mandatory. The practical test is whether the core can be exercised without the web server or database; mapping and additional interfaces have costs. - **documented**: Use-case-driven design: Start with the user’s purpose, inputs, primary processing, and exceptional outcomes. For an order, identify customer, shipment, and payment information; validate, create the order, and return an identifier or an error. Delay detailed data formats and delivery choices until needed. Use it to prevent framework directories from becoming the apparent purpose of the system. Keep the description concise: it is a design aid, not a demand for exhaustive forms or a prohibition on early UI work. - **inferred**: SOLID as a change-boundary review: For each module, identify the business function it serves and changes it must accommodate. Look for unrelated responsibilities, extension that requires widespread edits, substitute implementations that violate client expectations, interfaces larger than clients need, and high-level policy dependent on details. Choose a remedy against an actual change or client rather than applying all five mechanically. Martin later acknowledged accepting a substitution violation rather than paying the cost of additional interface segregation; the trade-off should be explicit. - **documented**: Design-decay diagnosis: Inspect rigidity, fragility, immobility, and viscosity. Ask whether changes cascade, unrelated behavior breaks, useful code is hard to reuse, or a shortcut is easier than a design-preserving change. Viscosity can come from the development environment as well as the code, such as slow compilation or source-control operations. Use symptoms to find troublesome dependencies and establish a boundary; do not treat a changing requirement by itself as the defect. - **documented**: Stable dependencies and abstractness: Count incoming package dependencies as Ca and outgoing dependencies as Ce; Martin defines instability as Ce divided by Ca plus Ce. A heavily depended-on package is costly to change, so he recommends directing dependencies toward stable packages and making stable packages sufficiently abstract to support extension. Use the metric to select packages for investigation, not as a score to optimize blindly. Some packages should remain easy to change, and the supplied PDF extraction does not support a reliable distance formula. - **documented**: Three laws and red-green-refactor: Write a failing test before production code; write only enough test to fail, including a compilation failure; then write only enough production code to pass. Alternate at roughly seconds, and use the minute-scale red-green-refactor cycle to separate making behavior work from improving structure. This discipline is useful when a behavior can be specified in small increments. It does not itself supply architecture or guarantee a good design, and exploratory or physical-edge work can need different treatment. - **documented**: Transformation Priority Premise: Distinguish behavior-preserving refactoring from a transformation that changes behavior to pass a test. Prefer a simpler transformation where possible, and choose the next example so the implementation can generalize incrementally. If the next test demands a large leap or a low-priority transformation, backtrack and try a simpler intermediate test. Use this as an experimental aid to test ordering, not a proof procedure: Martin explicitly doubts that his proposed ordering is final or formally established. - **documented**: TDD at multiple scales: Use seconds for the three laws, minutes for red-green-refactor, roughly ten minutes to ask whether specific examples are driving a more general implementation, and about an hour to reconsider architectural boundaries. When a test would require a large implementation jump, reconsider the sequence rather than abandoning small steps immediately. The intervals are Martin’s working heuristics, not measured thresholds. The larger-scale review counters the risk that attention to local tests obscures the system. - **documented**: Test contra-variance: Design tests as clients of a behavioral API rather than mirroring each production class. Start with public behavior, extract methods and cohesive classes behind the API, and retain the original tests as the implementation changes. Refactor tests as well as production code. The goal is shared behavioral coupling without identical structures: a behavior-preserving class rearrangement should not automatically force widespread test rewrites. Add narrower tests where they provide useful feedback, not simply because a class exists. - **documented**: Test-double selection: A dummy fills an unused argument; a stub supplies a controlled response; a spy records interactions; a formal mock also carries expectations; a fake implements some behavior and can itself require tests. Prefer doubles across significant boundaries such as databases and external services, rather than at every internal collaboration. More spying increases implementation coupling. Martin generally writes his own doubles, but allows tooling when it is useful, including for difficult-to-substitute interfaces. - **documented**: Test portfolio by purpose: In Martin’s proposed vocabulary, programmer unit tests check programmer expectations, business acceptance tests check business expectations, and integration and system tests check connections and configuration. Keep ordinary behavioral feedback fast by replacing slow infrastructure; retain real integration checks for the boundaries themselves. He considers a 15-minute unit-test feedback loop too slow and warns that suites taking more than a couple of minutes tend to be deferred. These are practical heuristics, not universal performance laws. - **inferred**: Boy Scout legacy improvement: When a feature or fix takes you into fragile code, make a small local improvement, such as clarifying a name or splitting a function, and gradually add tests. Leave unrelated areas untouched rather than launching an uncontrolled cleanup. Run a trusted regression suite after each safe step when one exists; where it does not, keep changes especially gentle. Martin expects this work to take months or years and prefers integrating even larger corrections with delivery rather than stopping the world. - **inferred**: Deployment escalation: Begin with clear plugin and package boundaries, then consider separate processes or services when a concrete need justifies them. Compare independent deployment, restart isolation, and technology choice against communication latency, debugging, configuration, coordination, and message-versioning costs. Martin’s 2014 recommendation starts with dynamically linked components and moves toward distribution as needed. A service boundary alone does not establish good separation of business responsibilities, and in-process packages can also support independent deployment. - **documented**: Design and iteration feedback: For a large effort, sketch a provisional architecture before coding; at iteration start, agree on a small design and revise the diagram when tests and implementation expose a mistake. - **documented**: Uncertainty-shaped estimation: Give optimistic, likely, and pessimistic durations, explain what accounts for the spread, and update the range as knowledge improves. Martin refers listeners to PERT but the supplied passage does not establish a formula he requires. When a date is fixed, negotiate a realistic feature set instead of implying certainty. His example of five, ten, and thirty days illustrates a range, not a reusable threshold or a promise that the worst case is bounded. - **documented**: Unnamed measurement-first performance loop: Make the behavior work, improve its structure with tests, measure the actual bottleneck, and optimize what the measurements identify. In a constrained real-time system, Martin describes extracting functions first and selectively undoing extraction when measured time or stack costs cause missed deadlines. Apply this when the relevant performance constraint can be measured; an architectural preference is not evidence that a deadline will be met.
