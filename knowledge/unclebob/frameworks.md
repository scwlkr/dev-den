# Robert C. Martin (Uncle Bob): frameworks

Built from 129 accepted distinct works and 527,818 source words. Compiled reasoning with source support and limits below.

- **documented**: TDD nano-cycle and red-green-refactor. Write only enough test to fail, including a compilation failure in Martin’s own practice; write only enough production code to pass; then improve structure while preserving behavior. Repeat in very small increments. Use it when behavior can be specified before implementation and fast feedback is available. If the next test requires a large implementation leap, choose a simpler case or backtrack. The sequence is a discipline, not a guarantee of good architecture; Martin also accepts other well-defined testing disciplines. - **documented**: Transformation Priority Premise. Distinguish behavior-preserving refactoring from transformations that add behavior to pass a test. Prefer simpler generalizing transformations and select tests that permit small steps; when an awkward low-priority change seems necessary, reconsider the test sequence. This is useful when a TDD exercise stalls or accumulates a branch for every example. Martin revised the ordering after a Fibonacci counterexample and tailored recursion versus iteration to language constraints. The ordering is a tentative heuristic, not a proven algorithm or a substitute for performance analysis. - **documented**: TDD cycles at multiple scales. Alternate second-scale test and production changes; refactor at minute scale; periodically ask whether increasingly specific tests are producing more general code; and, roughly hourly, inspect architectural boundaries and the placement of current work. Use the larger review to prevent a locally successful test cycle from losing the system picture. The intervals describe Martin’s working rhythm, not service-level targets. A high-level architectural vision still requires human judgment and is not automatically generated by TDD. ([unclebob-9d158b477bef4e](https://blog.cleancoder.com/uncle-bob/2014/12/17/TheCyclesOfTDD.html) / evidence unclebob-9d158b477bef4e-27518eeb868a; [unclebob-9d158b477bef4e](https://blog.cleancoder.com/uncle-bob/2014/12/17/TheCyclesOfTDD.html) / evidence unclebob-9d158b477bef4e-d2f2f58e6ea7; [unclebob-4f76a5b16635e3](https://blog.cleancoder.com/uncle-bob/2017/03/03/TDD-Harms-Architecture.html) / evidence unclebob-4f76a5b16635e3-8528582924bb; 2 independent supporting works)

- **documented**: Test contra-variance. Start with behavioral tests through a small API; extract private functions and cohesive classes behind that API without automatically creating matching test classes. Refactor tests too, but organize them around examples and client needs rather than the implementation’s class tree. Use this when harmless internal restructuring breaks many tests. Some behavioral coupling is necessary; the aim is to avoid structural coupling, not to make tests independent of the behavior they specify. More abstract inputs or a polymorphic interface can help when a test is too close to internals. - **inferred**: Test portfolio by purpose. Use programmer tests for detailed behavioral variations, business or QA-validated acceptance tests for business expectations, and integration or system tests for communication, startup, configuration, timeouts and load. Keep most feedback close to the code and use fewer, slower whole-system checks. Stub slow infrastructure where appropriate, but separately verify real queries and communication paths. Martin’s test names are his proposed vocabulary, not universally agreed definitions. A passing isolated test does not establish that physical hardware, a UI or the complete deployment works. - **documented**: Humble Object. Identify the hard-to-test physical, visual or framework boundary; move its decisions into ordinary testable modules; leave a thin adapter that transfers data or signals. Test the extracted behavior automatically and verify the remaining physical or visual result using an appropriate sensor, human observation or targeted system test. This is useful for CSS, device drivers and GUI layout where the correct outcome may require experimentation. It is not permission to leave substantial business logic untested merely because it sits near a screen. - **inferred**: Test-double choice, unnamed. First identify the purpose: a dummy fills an unused argument; a stub supplies a controlled answer; a spy records interactions; a formal mock also holds expectations; a fake implements simplified behavior. Prefer replacing slow or unreliable collaborators at significant boundaries, not automatically mocking every internal class. Excessive interaction checking makes harmless redesigns expensive; fakes can themselves become complicated. Martin generally handwrites named doubles but uses tools when their capabilities are needed. Retain some tests of real integrations. - **documented**: Clean Architecture dependency rule. Identify high-level policy and the external mechanisms it uses. Arrange every source dependency crossing a chosen boundary toward the higher-level side, even when runtime control flows outward. Put an input or output interface on the protected side and let an outer adapter implement it; pass simple data shaped for the inner side. Use this to test policy without a web server or database and to preserve implementation options. Four circles are illustrative, not mandatory, and independent deployment requires actual packaging and enforcement, not just a diagram. - **documented**: Use-case, interactor and entity separation. Describe a use case with inputs, primary processing, outcomes and exceptions without committing immediately to web forms or persistence. Implement the application-specific orchestration in an interactor; place reusable domain rules in entities; translate through plain request and response structures. This is useful when business behavior is scattered across controllers, views and persistence models. Martin credits Jacobson for the underlying model. The distinction is a design aid, not a requirement to create elaborate forms or layers before learning what the application needs. - **documented**: Presenter and humble view. Let the interactor return delivery-independent results. Have a presenter decide formatting and display state, such as dates, amounts, labels and disabled flags, and put them in a view model. The view transfers those decisions to the screen. Test the presenter without a server; Martin may check a sufficiently trivial view visually rather than automate it. Use this when UI testing is expensive but presentation decisions are important. Interactive JavaScript and nontrivial views still require appropriate testing. - **inferred**: Change-axis and abstraction selection, unnamed. Begin with a concrete solution and enough forethought to identify significant boundaries. Observe which changes recur and which unrelated concerns are affected. Group things that change together; separate those that change for different reasons; introduce an interface or other barrier where it protects a real axis of change or serves a concrete consumer. Use a simpler direct implementation for a one-off translation or disposable demonstration. There is no universal switch-count threshold, and an abstraction protects against particular changes, not every future request. - **inferred**: SOLID diagnostic. Ask which organizational responsibility drives a module’s changes; which expected extensions should leave existing code alone; whether implementations preserve client expectations; whether clients depend on interfaces they do not need; and whether high-level policy depends on low-level detail. Apply the answers to concrete change propagation, not as a score requiring maximum abstraction. A mutable square can violate a rectangle client’s setter expectations, while a different contract may not. Martin later clarified that substitution also applies to interface implementations and duck types, not only inheritance. - **documented**: Design-decay diagnosis. Examine rigidity, where changes spread; fragility, where unrelated behavior breaks; immobility, where useful code cannot be extracted; and viscosity, where a hack is easier than a sound change. Include the development environment: slow compilation or source-control operations can also make good work difficult. Use these symptoms to investigate dependencies and feedback costs, not to blame changing requirements. Compare the cost of a boundary or extraction with the actual change pressure before adding another abstraction. - **documented**: Package stability and abstractness. Inspect incoming coupling and outgoing coupling; Martin defines instability as outgoing coupling divided by the sum of incoming and outgoing coupling. A package with many dependents is costly to change, so stable packages need suitable abstraction if clients must extend them. Look for dependency cycles and break them through shared packages or dependency inversion. Use the measurements as prompts for review, not a complete architectural score: Martin explicitly warns against relying on the metrics alone, and some components should remain easy to change. - **documented**: Boy Scout legacy improvement. When already changing fragile code, make one gentle improvement, such as a clearer name or a small extraction, and gradually add tests around the area. Leave unrelated areas alone; use the expanding safety net for subsequent work. This is useful when a whole-system cleanup would be risky or hard to fund. Martin expects progress to take months or years and cautions against a separate, open-ended cleanup project. For an urgent outage he allows a messy short-term fix, with an opportunity to clean it afterward. - **inferred**: Readable-function review, unnamed. Look for mixed levels of abstraction, surprising side effects and pieces that can be given meaningful names. Extract when doing so clarifies the main sequence, and place lower-level functions where a reader can follow them. Martin likes functions around four to six lines, but treats a ten-line function as a reason to investigate, not reject it. If extraction creates excessive navigation, inline to understand the code and repartition or rename. In constrained real-time work, measure and undo selected extractions if their overhead violates deadlines. - **inferred**: Deployment scale, unnamed. Start with well-separated components and a plugin architecture; consider separate processes or services when a concrete need such as scalability, independent operations, failover or security justifies them. - **documented**: Short-iteration planning game. Estimate stories relatively, measure completed work per iteration, forecast the remaining work and communicate bad news early. - **documented**: Three-point uncertainty estimate. Break poorly understood work into tasks, then communicate optimistic, nominal and adverse outcomes and revise them as evidence arrives. In one account Martin associates these with 5%, 50% and 95% cases; in other examples he uses illustrative durations rather than calibrated probabilities. Use the range to expose uncertainty to decision-makers, not to disguise the nominal case as a guarantee. A fixed deadline can still be a business constraint: respond with the scope plausibly achievable by that date. - **documented**: Voluntary pairing by problem depth. Pair on nontrivial work to share knowledge, review surrounding code and support continuity; for a seemingly deep problem, begin together and separate if it proves irreducible and demands concentration. Trivial work may not justify pairing. Martin’s 2021 guideline is 20–40 minutes per session and no more than three or four consecutive sessions, not a rule; he suggests a mature team might pair half the time or less. He opposes manager-mandated or tracked pairing and warns against pairing to the point of resentment. - **documented**: Agent verification loop, experimental. Constrain generated work with unit tests, coverage and complexity checks, bounded mutation testing, and human review of intended behavior. A surviving mutant can expose execution that assertions do not meaningfully check, but some mutants cannot or should not be killed.
