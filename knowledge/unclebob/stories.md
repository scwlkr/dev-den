# Robert C. Martin (Uncle Bob): stories

Built from 61 accepted distinct works and 268,975 source words. Compiled reasoning with source support and limits below.

- **inferred**: Pairing with Kent Beck. Martin says he initially dismissed test-first development, then paired with Beck on a small animated application using tiny alternating test and code steps. He observed that the two-hour exercise proceeded without their using a debugger; months of subsequent practice helped convince him of the method. The operational lesson is to try a disciplined feedback loop before judging it from a description. The debugger observation belongs to that exercise, not a promise that TDD eliminates debugging. - **inferred**: FitNesse without the planned database. Martin recounts working with his son on FitNesse while postponing MySQL: the team first used a mock, then an in-memory hash table, then flat files. He credits Michael Feathers with the flat-file implementation. A customer later implemented a MySQL plugin, but Martin reports it was not widely used. The case illustrates building useful behavior while preserving a storage option; it does not show that flat files suffice for systems with different query, scale or operational needs. - **inferred**: FitNesse tests that mirrored classes. Martin reports that he once praised the project's one-to-one correspondence between production classes and test classes. Over time he experienced fragile tests and rigidity, and says the project reduced that correspondence in later code. His revised lesson is to design tests as clients of behavioral interfaces rather than reproduce every internal class boundary. The account supports a warning about this project, not a rule that every direct class test is harmful. - **inferred**: Rails directories and architectural intent. Reviewing a Rails application his son gave him, and later discussing an old application of his own, Martin recognized the framework from the directory structure but could not see the application's purpose. He used the experience to argue that use cases should be prominent and delivery mechanisms should be peripheral. A directory listing is a useful question to ask of a design; it does not by itself establish whether the code is coupled or whether a Rails application cannot be well structured. - **inferred**: Dijkstra exercise and regression. In a 2016 worked TDD example, Martin found that changing an AND to an OR passed a new two-edge case but broke degenerate cases. A special case based on edge count was too specific, so later tests drove graph traversal, branching and shorter-path updates. He judged the sequence jerky rather than a smooth derivation, and described the resulting directed-graph implementation as inefficient and needing cleanup. The case supports running the whole relevant suite and seeking generality, not assuming TDD automatically produces an efficient algorithm. - **inferred**: Word wrap and a bad next test. In his tentative Transformation Priority Premise, Martin describes an implementation that replaced every space with a newline to pass a two-word wrap test. The next three-word case demanded an uncomfortably large step. He postponed it and tested breaking a long word first, creating a more incremental route. The lesson is to reconsider test order when the next failure requires a large rewrite. He explicitly regarded the proposed transformation ordering as uncertain, not a proven algorithm for selecting tests. - **inferred**: Diamond-Square and a faulty expected value. In 2017 Martin tested coordinate-level operations with spies because complete output arrays obscured incremental progress. - **inferred**: C++ client with slow links. Martin advised a client whose small test suites still incurred several-minute build and link delays. He recommended smaller linked libraries, unidirectional concrete-to-abstract dependencies, and replacing the testing tool if it was the bottleneck. The lesson is to inspect build architecture and tooling as part of feedback design, rather than merely asking developers to run tests more often. The evidence records his recommendation, not a measured outcome after adoption. - **inferred**: A disposable visual-effects program. Martin reports writing an approximately 100-line, one-use visual-effects program without tests, using a Clojure REPL and immediate visual feedback. Its disposable and predominantly graphical character made him accept the risk. Elsewhere he says exploratory code may receive tests afterward or be discarded and rewritten test-first. The example limits a blanket interpretation of his TDD advocacy; it does not justify omitting tests from durable business logic. - **inferred**: The flat-file startup dispute. Martin recalls opposing a relational database at a 1980s startup because the existing simple application did not need complex queries or extensive reporting, while the database imposed cost and resource overhead. He says marketing insisted customers would require it despite none having raised the need, and he later left the company. The case illustrates matching infrastructure to demonstrated requirements; it is his retrospective account, not proof that the marketing concern or a relational database would always be misplaced. - **inferred**: Craft Dispatch System. Martin says he chose multiple communicating processes for a 1984 telephone job-dispatch system on a resource-constrained machine, rather than the single executables used in earlier systems. A shared data process, table-driven state machines and short-lived command-line actions coordinated sessions and events. He later drew parallels with modern service and message-bus ideas. The comparison is retrospective: modern product names were not technologies used by that system, and the historical constraints differ from current distributed deployments. - **inferred**: Manual regression under budget pressure. Martin recounts a QA manager facing a budget cut in 2008 while responsible for 80,000 manual tests. Choosing which tests to omit made regression confidence difficult, especially when late development compressed QA time. He advocates automating repeatable scripted checks while retaining human exploratory testing. The account illustrates a scaling risk in a particular process; it does not establish that automation eliminates maintenance costs or replaces all human judgment. - **inferred**: A threatened staffing change. Martin recounts objecting when other managers planned to remove people from a project for which he had promised delivery. He expected the confrontation might cost him his job, but says the managers accepted his point. His lesson is to make the resource assumptions behind commitments visible and defend them rather than silently accept an impossible plan. The outcome is anecdotal; the personal risks and authority available to another developer may be very different.
