# Casey Muratori: frameworks

Built from 36 accepted distinct works and 425,131 source words. Compiled reasoning with source support and limits below.

- **inferred**: Performance budget and optimization path — unnamed. Start with the job the product must do and identify the resources users pay for: elapsed time, CPU, battery, network traffic and storage. Establish an acceptable budget, then examine whether the architecture leaves a credible route to it. Batch independent network requests and avoid embedding unavoidable round trips inside individual object operations. Delay detailed tuning if a slow component can be replaced locally; investigate earlier if meeting the budget would require redesigning the system. This is a decision framework, not a demand to maximize every metric. - **inferred**: Hardware ceiling and gap investigation — unnamed. Count the work required by the actual task; estimate plausible arithmetic throughput, SIMD width, relevant memory bandwidth and available parallelism. Measure the implementation and compare it with that rough range. A large gap warrants examining hidden work, data movement and assumptions; a small gap may justify stopping. In one discussion he treats roughly twice an estimated practical range as potentially reasonable, but that is a local judgment, not a universal threshold. A theoretical ceiling is a diagnostic reference, not a prediction that real code will reach peak throughput. - **documented**: WARMED cost review. Consider the costs of writing, agreeing on, reading, modifying, executing and debugging code. For each proposed practice, identify which cost it is supposed to lower, how that effect could be observed, and which other costs may rise. Compare equivalent delivered behavior rather than rewarding fewer lines or a familiar pattern in isolation. Muratori gives execution particular weight because users pay for it, but explicitly warns against optimizing one category to the exclusion of the others. Use the checklist to structure a trade-off, not as a replacement ritual. - **inferred**: Workload-first specialization — unnamed. For a slow path, step through the actual calls and compare useful work with allocations, traversal and general-purpose machinery. Identify facts that remain invariant across a batch, gather them once, and choose a representation for the real query. In The Witness grass-placement case, Muratori describes collecting local geometry before the raycasts and using a two-dimensional grid because the rays point downward. This trades setup and storage for cheaper repeated queries. It is appropriate when repeated work amortizes the prepass, not evidence that general-purpose raycasting structures are intrinsically bad. - **inferred**: Core loop before parallel distribution — unnamed. First remove unnecessary work and data traversal. Then establish what the remaining loop does, whether independent work can be grouped into SIMD lanes, and whether the relevant cache or memory can supply it. Consider threads after understanding the code each worker will run. In the grass case he describes eight-wide triangle processing, lane-local best hits and a final reduction; he stopped with one thread once the result was fast enough. A many-core target can change the payoff. The captions describe the method but do not supply the demonstrated code. - **inferred**: Benchmark-purpose separation — unnamed. Decide whether a test is intended to compare practical alternatives or isolate a mechanism. For comparison, use multiple representative workloads, inspect source and ensure implementations receive comparable expertise; account for shared native libraries and startup or initialization costs. For a microarchitectural question, a tiny artificial loop can be useful precisely because it isolates behavior, but its result does not rank languages generally. Inspect generated code and target options, and check whether the test accidentally prevents the compiler optimizations that ordinary users want. - **inferred**: Model, measure, revise — unnamed. Derive a prediction from dependencies, then check what the timer actually measures and corroborate surprising results with another instrument. In the missing-increment investigation, the initial model predicted about one core cycle per iteration; the timestamp counter was not itself a core-cycle counter, and frequency differences alone did not explain the observed result. Hardware counters supported unusually high instruction throughput. Muratori proposed dependency reassociation as a possible mechanism, not a verified implementation, and suggested varying instruction sequences and counters to discriminate alternatives. - **inferred**: Experiment-derived APIs — unnamed. Implement a needed capability and at least one straightforward client before deciding its reusable interface. For broader reuse, try several materially different real clients and derive the common boundary from working code. Existing experience can supply some of this evidence, and a design document can precede production when it reports experiments rather than imagined usage. For difficult problems, validate implementation constraints before fixing an interface that might rule out workable solutions. Apply early because changes to a widely used API multiply across its clients. - **inferred**: Stable exposure and escape hatches — unnamed. Identify representations the library can responsibly promise, expose those for direct use, and supply useful operations around them. - **documented**: Single-path immediate-mode UI. Let application-controlled update code call UI operations and handle their results in the same path. Keep application values in the application; maintain shared interaction state such as hot and active item IDs, plus control-specific state where needed. Choose identifiers that represent the desired identity across frames. In the described button, mouse-down activates a hot item and release reports a click only if it remains hot. - **inferred**: Boundary and communication audit — unnamed. Map operations that must evolve together, organizational ownership and existing software boundaries. A boundary can enable parallel work or make a complex system understandable, but coordination and joint optimization across it become more expensive. Place necessary divisions where that cost does least damage; do not infer that an organizational split explains every additional class or service. Muratori's Conway's nightmare adds a temporal warning: old code may retain boundaries from successive past organizations. Treat the model as a useful hypothesis, not a physical law. - **documented**: Deferred conflict resolution — unnamed. Preserve each user's local edit as primary and retain competing versions visibly as alternatives. Let people save and share before reconciling if the work permits it; resolve when a changed shared API, compilation failure or other real dependency requires it. Muratori describes this for his own small-team system, including work across two machines. It separates backup from the timing of a merge, but does not establish that the same interface scales to a hundred developers. He would study that workflow before claiming a larger-team solution. - **documented**: Repeated-filter stability test — unnamed. Apply the half-pixel filter repeatedly, reverse the accumulated one-pixel shift after each pair of passes, and compare with both previous iterations and the original image. Stop when the output converges or crosses a declared failure criterion. In his experiment, explosion means average channel error of 64/255 or a maximum channel error of 255; these are test-specific thresholds, not universal quality standards. Search between a stable integer kernel and a sharper unstable one when additional computation is affordable. Quantization affects error accumulation, so infinite-precision analysis alone is insufficient. - **inferred**: Research the claim behind the slogan — unnamed. State the disputed rule quantitatively, follow its citations to the underlying study, inspect what was actually measured, and distinguish counts of execution from time samples. - **inferred**: Learning allocation — unnamed. Learn durable concepts in advance when ignorance would prevent recognizing an opportunity: basic assembly reading, approximate CPU and memory costs, SIMD and latency versus throughput. Learn details just in time when the need will announce itself, such as a particular deployment format. Use a compiler-output explorer, small timing experiments and generated-code inspection to build intuition. This prepares programmers to recognize unreasonable slowness without requiring everyone to become an assembly author or specialist optimizer. - **inferred**: Prototype, assess, replace — unnamed. Build a small working version to expose design and product unknowns, observe what fails with real users or clients, test alternatives, and then apply the successful design systematically. A deliberately disposable slow implementation can be reasonable for time to market, but the team needs the skills and an actual plan to replace it. Do not let a prototype's serial dependencies harden indefinitely into architecture under the assumption that profiling a few hotspots will repair everything.
