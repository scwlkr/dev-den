# Casey Muratori: frameworks

Built from 87 accepted distinct works and 1,166,408 source words. Compiled reasoning with source support and limits below.

- **inferred**: Performance-aware architecture — unnamed. First define the job and its resource budget: elapsed time, CPU, battery, network, or storage, not speed in isolation. Identify large batches, data movement, and serial dependencies before choosing interfaces. Then ask whether a credible path to the budget remains without changing those interfaces. Defer detailed optimization if the path is clear; investigate or redesign if every request must wait on the preceding request. A deliberately slow first release can be reasonable, but it needs a replacement plan and the skills to execute it. No universal numerical threshold is established. - **inferred**: Hardware ceiling and gap analysis — unnamed. Enumerate the necessary work, estimate arithmetic throughput and the bandwidth needed to feed it, and account for data reuse, dependencies, and the cores actually used. Measure the implementation and compare it with the resulting plausible range. A large gap directs investigation toward unnecessary work or a mistaken model; the theoretical ceiling is not a promised result. In one discussion Muratori regarded roughly within 2× of an estimated practical range as potentially reasonable, explicitly as a ballpark for that situation, not a general acceptance threshold. - **inferred**: Divide-and-conquer profiling — unnamed. Keep a coarse view of recurring subsystem costs and frame spikes. When a region is unexpectedly expensive relative to its work, subdivide it with timing blocks and eliminate candidates. Preserve event history and thread attribution when overlap or a past stutter matters. In Handmade Hero, roughly two million cycles attributed to input justified further instrumentation even though Muratori already suspected controller polling. That number is a case-specific trigger, not a threshold for all input code. Instrumentation itself can perturb execution, so validate suspicious results with other observations. - **inferred**: Benchmark by purpose — unnamed. Decide whether the test explores one mechanism or compares general-purpose implementations. For exploration, isolate a small instruction sequence and predict its dependency chain; unusual behavior can be informative precisely because the workload is artificial. For comparison, use multiple relevant workloads, inspect implementations, and account for startup, data representation, shared libraries, compiler targets, and programmer skill. An almost-empty loop or a deliberately inhibited compiler cannot establish a language ranking. Record the machine and workload alongside the result. - **inferred**: Investigate an impossible measurement — unnamed. State the expected mechanism, check what the timer actually measures, compare clock specifications, and seek independent counters before inventing a hardware explanation. In the 2024 missing-increment investigation, timestamp-counter ticks could not by themselves be equated with boosted core cycles; the reported ratio exceeded the plausible boost explanation, and hardware counters supported unexpectedly high instruction throughput. Muratori then proposed a renaming hypothesis but did not claim to have proved it. Vary instruction sequences and counters if suitable hardware is available. - **inferred**: Usage-first API design — Stuffalupagus-oriented programming in one Handmade Hero example. Write the client operation as though the facility exists, including the information and result the caller needs. Implement enough of the supporting representation to make that use work, then revise against real clients. A file-read test exposed that returning a pointer without its size was insufficient. Use this approach when call-site friction or missing information is uncertain; imagined usage is a starting hypothesis, not a substitute for exercising actual implementations and failure cases. ([casey-1e33b627de9aaf](https://www.youtube.com/watch?v=y7-phAHpweU&t=1940) / evidence casey-1e33b627de9aaf-f8a9085c9f39; [casey-4dbdb3d822fbe3](https://www.youtube.com/watch?v=kdAte9pdLv8&t=3077) / evidence casey-4dbdb3d822fbe3-ca8e53abb775; [casey-b0bfe208802c4c](https://caseymuratori.com/blog_0025) / evidence casey-b0bfe208802c4c-b931511d7e9f; 3 independent supporting works)

- **inferred**: Compression-oriented programming, also called semantic compression. Write straightforward concrete code, let real repetitions and requirements appear, and extract common operations or representations. Explore alternatives before condensing them into the smallest set that preserves needed behavior. Apply this when the requirements are still being discovered: duplicated provisional code can be cheaper than a prematurely fixed abstraction. Once callers are understood, centralize repeated setup or cleanup so implementation details can change. Do not compress away a feature merely to reduce code; verify what each representation enables. - **inferred**: Operation-oriented representation — unnamed. List the actions that must run across the data, the information each consumes, and the changes expected most often. Compare a hierarchy organized by domain type with properties grouped for those operations, or with tagged alternatives. Prefer a discriminated union when alternatives are mutually exclusive; consider feature flags when an entity combines independent features. For a heterogeneous editor, property collections can make cross-cutting edits easier. Entity-component systems are an option, not a universal prescription; Muratori says he does not personally use them as a general answer. - **inferred**: Stable representation contract — unnamed. For reusable libraries, discover which data representations and behaviors can actually be promised, expose those deliberately, and provide useful operations over them. Keep genuinely unsettled internals private; where customers have incompatible needs, accept their representation rather than forcing conversion to an arbitrary one. Escape hatches let a later programmer address an omitted use case while knowingly accepting compatibility risk. Granny 2 design was collaborative with Jeff Roberts; the lesson does not establish that every internal detail should be public. - **inferred**: Single-path immediate-mode UI — his named API model, not a claim about every implementation. Application update code calls UI operations and handles their results in ordinary control flow; application data stays with the application. A shared context tracks the hot and active items, with additional editing state where needed. IDs must remain meaningful across frames. In his spoken button example, mouse-down activates a hot item and release reports a click only if it remains hot. Consider this for real-time tools; layout discovery may introduce a frame of lag, and selective redraw can be harder. - **inferred**: Looped live editing — unnamed. Reach the interaction to tune, capture both starting game state and subsequent input, repeatedly restore and replay them, and reload code while observing the same interaction. A fixed-address game-memory block permits raw restoration of internal pointers when all relevant state is actually inside it. Capture random-generator state too; threading and external inputs can still prevent deterministic replay. Data-layout changes and code or vtable pointers can invalidate saved state after reload. This is principally a tuning tool, not automatic migration or a production rewind design. - **inferred**: Platform/game boundary — unnamed. Identify what varies by platform and what the game actually needs. Let platform code own startup and translate native input, memory, video, and sound into a small game-facing contract; move genuinely common behavior above that boundary. Add queues or callbacks where real disk and network needs require them rather than insisting on one synchronous call. Judge portability by initial porting effort, achievable performance, and maintenance when shared code changes. A virtual operating-system interface is also viable; inversion is most attractive when required flexibility is asymmetric. - **inferred**: Batch and specialize the actual workload — unnamed. Step into the running path, identify work repeated for every item, and separate invariants into a prepass. Select a representation for the query actually performed, then simplify and vectorize the remaining kernel if worthwhile. - **inferred**: Preserve causes, not just symptoms — unnamed. Reproduce the failure, isolate the stage where it appears, trace values through actual boundaries, and state what a proposed cause predicts before inspecting further. Understand the purpose of the existing code before deleting it. In his 2012 Witness stall investigation, removing a hook stopped the symptom, but he investigated and restored its intended behavior; his explanation of Windows internals remained partly unverified. For rare temporal bugs, retain queryable history or checkpoints because stopping after the symptom may be too late. - **documented**: WARMED cost checklist. Examine the costs of writing, agreeing on, reading, modifying, executing, and debugging code. For a proposed convention, identify a concrete outcome it should improve and how that improvement could be observed; include runtime costs borne by users and later rewrite costs. Use the checklist to compare alternatives, not as another ritual or numerical score. Muratori considers execution especially important, but explicitly rejects optimizing any one cost to the exclusion of the others; productivity and architecture are difficult to measure conclusively.
