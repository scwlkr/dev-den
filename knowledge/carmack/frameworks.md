# John Carmack: frameworks

Built from 24 accepted distinct works and 471,558 source words. Compiled reasoning with source support and limits below.

- **inferred**: Problem–goal–tools loop — unnamed. Define the user-visible problem and a concrete goal, list the tools and constraints, implement a candidate, and repeatedly check progress against the goal. For prioritization, compare expected benefit with effort, side effects and destabilization risk; do not treat technical novelty as a benefit by itself. Useful when a backlog contains many plausible improvements. Inferred guidance: reject or defer work that cannot plausibly change the product enough to repay its integration and maintenance costs. Carmack’s 2000 Quake III backlog example included improvements that could take a day yet destabilize other behavior. - **inferred**: Adversarial idea testing — unnamed. Keep several questions active, draw on varied reading and practical work, record ideas, then deliberately attack the assumptions that would make each proposal fail. Prototype promptly when possible and compare alternatives rather than defending the first elegant answer. Useful for engine research and architectural uncertainty. A fatal counterexample is a successful test, not a personal defeat. Carmack acknowledged becoming attached to an untested rocket-tank idea; his rendering research also used multiple implementations. An experiment remains weaker evidence than a representative production workload. - **inferred**: Whole-system bottleneck accounting — unnamed. Measure the representative application, identify the fraction affected by an optimization, estimate its maximum possible overall gain, and include dispatch, driver, memory and integration costs. If only 20% of runtime is accelerated, even making that part free caps overall speedup at 1.25 times. Use scene-level tests as well as isolated kernels. In 1998 Carmack found Quake II on Voodoo 2 setup-limited rather than fill-limited; changing geometry submission could move the bottleneck. Timedemos also omit some game logic, so do not equate their scores with complete gameplay performance. - **inferred**: Latency budget and bypass — unnamed. Trace the path from physical input through sampling, game logic, jobs, rendering, buffering and display scanout. Measure end to end with a high-speed camera or equivalent instrumentation; distinguish a simplified input-to-color test from real gameplay. Then remove queues or bypass a deferred stage for urgent feedback. Rage’s animation pipeline added a frame to weapon response, motivating an early firing effect. Smoothing can trade jitter for lag: his 1998 mouse filter added roughly 12 ms. Use these numbers as historical examples, not modern targets. - **documented**: Frame deadline management — unnamed. Establish the presentation deadline, test expensive scenes and spikes, then choose which quality or presentation constraint can yield when the budget is exceeded. Rage targeted 60 Hz and reactively reduced resolution; if a surprise spike still missed the deadline, it temporarily allowed tearing rather than repeatedly falling between 60 and 30 fps. Carmack considered informing the renderer about impending effects so it could adapt earlier. This is a product-specific compromise, not a blanket preference for tearing. For VR, missed deadlines and scheduling jitter have different comfort consequences. - **inferred**: Failure-pattern review and static analysis — unnamed. Record recent crashes or subtle defects, look for recurring causes, change the structure that permits the mistake, and add automated detection to normal builds. Carmack’s six-month error log found three copy-paste component mistakes; a loop, template or object could remove the repetition. Treat warnings as actionable for maintained code, including cases where a false warning exposes opaque assumptions. But manage analyzer noise: he did not clear all PC-lint warnings, and clean results from one tool did not establish defect freedom. - **inferred**: Frame archaeology — unnamed. Periodically single-step through a complete frame, skipping repetitive loop bodies, and write down unexpected calls, state changes, ordering and work that should not run. Keep once-per-frame work visible near the outer loop where that improves comprehension; distinguish source-level inlining for visibility from an unproven function-call performance win. Use this on mature engines where fixes and subsystems have accumulated. Carmack cautioned that some untidiness remains because making the game work also matters; do not rewrite every discovered imperfection without measuring its consequence. - **inferred**: Functional core, practical boundaries — unnamed. Identify a state-entangled operation, gather explicit inputs, calculate results in a self-contained function, and apply required effects at the boundary. Prefer reducing heavily tangled state over spending equivalent effort perfecting an already simple function. Value inputs can support safe concurrent use, but a const reference is not safe if another thread mutates or frees the object. Copying large framebuffers or containers may be too expensive, so mutation or output parameters can be justified with weaker guarantees. Adopt this incrementally in existing C++ rather than assuming a whole studio can cheaply change languages. - **inferred**: Parallelism with explicit latency costs — unnamed. First isolate expensive, batchable operations; keep creative game logic straightforward where practical; dispatch collision, pathfinding or animation jobs and consume results later. Measure whole-game gain and any added response frame. Carmack’s existing architecture used this compromise instead of pervasive locks. His alternative snapshot-and-event entity model was unfinished research: independent entities can both enter a seemingly empty narrow passage, requiring conflict resolution. Use the production pattern when latency permits; do not present the snapshot proposal as a solved general game architecture. - **inferred**: Sandbox versus native code — unnamed. Start with the trust boundary and distribution model, then compare execution speed, debugging, portability and enforceable isolation. In 1997 Carmack considered native DLLs for Quake II game logic, estimating a 5–10% whole-game improvement and valuing ordinary debuggers. In 1998–99, downloadable client mods pushed him toward C compiled for an isolated VM with restricted system calls. Native modules remained useful in selected debugging or server contexts. After interpreter performance missed target, he implemented dynamic compilation: one test scored 52.9 native, 50.2 compiled and 43.9 interpreted, with greater generated-code size. Sandbox security remains a design claim, not independent verification. - **inferred**: Real-world networking budget — unnamed. Separate bandwidth, latency, loss and buffering; instrument snapshots and prediction rather than using ping as the only explanation. On a constrained link, cap sending before queues accumulate: fewer updates may look choppy but can avoid severe delay. QuakeWorld replaced a reliable-stream foundation with unreliable packets and, in Carmack’s 1996 example, promptly processed client packets while accepting complications from nonuniform world time. Quake III later favored client prediction for responsive local control, even though remote movement could be jerky. Dial-up observations are historical examples, not present-day bandwidth settings. - **inferred**: Representative renderer comparison — unnamed. Identify the visible artifact or workload, trace the approximation that causes it, implement plausible alternatives, then compare image quality, draw count, memory and target-hardware cost. Doom 3’s interpolated half-angle could distort highlights across large triangles; Carmack discussed a more accurate reflection-vector calculation. For shadows, a favorable spotlight demo hid the repeated geometry rendering required by common point lights. Shadow volumes suited Doom 3’s hardware era; shadow buffers were a possible later choice, but his newer path was still slower at the time. Do not generalize a demo or historical hardware result into a universal ranking. - **inferred**: Virtual texture production test — unnamed. Treat authored detail, page granularity, feedback, storage latency, decoding, cache capacity and GPU upload as one pipeline. Test worst camera movement and slowest supported storage, not only favorable installed demos. Rage used optical media, disk and RAM caches before GPU texture storage; page fragmentation and platform constraints made its production system more complex than the initial concept. Carmack’s approximate worst-case DVD example took up to 15 seconds for all detail to arrive. The benefit was artist-controlled unique surfaces; costs included streaming artifacts, data size and less general dynamic lighting. - **inferred**: VR deadline and thermal design — unnamed. Budget for sustained operation, not peak clocks; choose CPU/GPU balance for the application and define degradation or exit behavior. - **inferred**: Tracking and locomotion trade study — unnamed. Compare tracking candidates on latency, coverage, precision, drift and failure behavior, then test movement with users. Carmack’s 2012 comparison found approximately 70 ms processed latency too high in one camera-based approach; another lost tracking at its field boundary, while magnetic tracking degraded more gracefully but had orientation error. For exploration he preferred physical turning where practical, with controlled forward movement; simulated continuous yaw can cause discomfort. His optical-flow velocity proposal was explicitly research, not proof that relative tracking solves drift or positional accuracy. - **inferred**: Production risk before polish — unnamed. Block out gameplay, test unfamiliar mechanics early, and invite experienced feedback while changes are still affordable. Preserve a cheap test environment even if final art and lighting require longer processing. Carmack said earlier projects repeatedly committed to visual showpieces before gameplay was settled; Rage’s driving was deliberately investigated early, while other design risks still needed whole-game evaluation. A functional demo is not a production engine: account separately for tooling, integration, maintenance and platform work before promising a delivery date. - **inferred**: Target-platform continuous development — unnamed. Define the minimum device and its input, memory, thermal and distribution constraints; build and test all supported platforms throughout development. A shared source base does not mean accepting the easiest common denominator: spend platform-specific effort where it materially improves the result. Carmack regretted allowing Quake II portability to slip under Windows-only development, and later described regular cross-platform builds for id Tech 5. His later Quest advice similarly favored designing around the lower-performance target rather than assuming a desktop prototype would transfer. - **inferred**: AI evaluation by task and embodiment — unnamed. For game AI, first specify the player experience: simple behaviors can produce convincing apparent intent, while stronger autonomous opponents may be more valuable in multiplayer. For general learning research, separately test whether an agent can operate continuously and whether results transfer from simulation to a physical setup. Carmack’s 2020 continuous-agent view was a hypothesis, not a demonstrated architecture; in 2025 he described Keen testing with a camera, television and robot-operated joystick. Passing a physical test improves validation for that setup, not proof of general intelligence.
