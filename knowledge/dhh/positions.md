# David Heinemeier Hansson (DHH): positions

Built from 200 accepted distinct works and 505,611 source words. Compiled reasoning with source support and limits below.

- **documented**: Integrated monoliths: Start and usually stay with one comprehensible application, organized with modules rather than network boundaries. Remote calls introduce latency, failure handling, deployment coordination and synchronization that in-process calls avoid. Extraction becomes attractive when an evolved, well-bounded component has substantial measured performance or organizational benefits. In 2016 he described Basecamp as a monolith with satellites, not a prohibition on all services. ([dhh-2a86f6e005b2cb](https://se-radio.net/2016/06/se-radio-episode-261-david-heinemeier-hansson-on-the-state-of-rails-monoliths-and-more/) / evidence dhh-2a86f6e005b2cb-02db82abcf4f; [dhh-8765f99e418f64](https://world.hey.com/dhh/how-to-recover-from-microservices-ce3803cc) / evidence dhh-8765f99e418f64-c9a2162fb1fb; [dhh-499fccc4f75714](https://world.hey.com/dhh/even-amazon-can-t-make-sense-of-serverless-or-microservices-59625580) / evidence dhh-499fccc4f75714-75154edec3fb; 3 independent supporting works)

- **documented**: Architecture and scale: Rails is principally designed for the individual or small team building a real application, even though large businesses can use it. DHH estimates that Basecamp- or HEY-sized applications of just over 100,000 Ruby lines can be understood by one person; he treats much larger systems as increasingly difficult. These are rough judgments, not thresholds. Shopify's reported five-million-line monolith demonstrates both Rails' range and organizational challenges beyond his ordinary experience. ([dhh-2077549712371a](https://lexfridman.com/dhh-david-heinemeier-hansson-transcript/) / evidence dhh-2077549712371a-c12cb93e9576; [dhh-2077549712371a](https://lexfridman.com/dhh-david-heinemeier-hansson-transcript/) / evidence dhh-2077549712371a-b5f04f2e331c; [dhh-c1503a025ccd63](https://world.hey.com/dhh/joining-the-shopify-board-of-directors-3c351fbb) / evidence dhh-c1503a025ccd63-09a64138623b; 2 independent supporting works)

- **documented**: Recovering from premature services: Stop introducing new services, choose an existing service as a center, and consolidate coherent critical flows such as signup or checkout first. Leave an isolated hotspot separate if benchmarks show that its performance benefit warrants the productivity cost. He recommends keeping backend language diversity low, but this is a heuristic: consolidation itself has migration costs and does not repair poor internal design automatically. - **documented**: Full-stack Rails: Judge framework simplicity by the whole application-building job, not framework line count or the size of each individual library. A larger integrated toolkit can eliminate application code, configuration and integration work across common problems. This comes with a broad API and framework complexity; DHH does not treat a small public method count as an overriding goal. - **documented**: Defaults and conventions: Choose a coherent, preassembled stack and infer routine details such as naming and associations, leaving developers to spend attention on consequential product choices. Shared conventions also permit deeper abstractions and common troubleshooting. Defaults should be replaceable when a real need warrants it; departing from them has integration and learning costs, but enforced uniformity would deny legitimate exceptions. - **documented**: Framework features: Extract reusable tools from actual applications, then compare real code before and after a proposed addition. The bar is whether it materially improves a demonstrated use case, not whether the feature sounds generally useful. DHH acknowledges that some of his own ideas fail that comparison and that speculative framework inventions have produced bad features. Other contributors' application needs also inform Rails. - **documented**: Ruby and programmer happiness: DHH accepts runtime and implementation costs for expressive code that people enjoy reading and writing. Ruby's multiple ways to express a thought can improve local fit, but maximum brevity is not the goal: compressed code can become opaque. He regards happiness as an end as well as a possible productivity benefit, not an objectively proven advantage for every developer. - **documented**: Static and dynamic typing: He prefers dynamic languages and removed TypeScript from Turbo because annotations and generic typing complicated his metaprogramming and no-build workflow, while IDE completion mattered little to him. He recognizes that other developers value static tooling and may make the opposite trade-off. His later account explicitly rejects his earlier crusade to convert everyone to his preferred tools. - **documented**: Active Record and SQL: Combining persistence and domain behavior is a practical trade for database-backed web applications. Mapping tables to classes and rows to objects removes repetitive wiring without pretending the relational database has disappeared. Use direct SQL where the abstraction fits poorly and learn SQL even when an ORM makes the first application easy. He later reports that Basecamp 5 may need no complete SQL statements, not that SQL knowledge is obsolete. - **documented**: Resources and domain modeling: CRUD is a useful constraint for finding missing concepts, not a universal law. A relationship with its own authorization or history may deserve a membership or subscription model and ordinary create or destroy actions. For a small state change, a dedicated action can be clearer than inventing an elaborate object. Keep necessary domain side effects out of a controller merely to preserve a superficially neat route. - **documented**: Testing and design: DHH moved away from mandatory test-first development after finding that it often led him toward more indirection rather than clearer designs. He remains a strong advocate of automated regression tests, including model tests against a real database and system tests through the assembled application. Test-first can still be useful when inputs and expected outputs are already clear. Testability is one consideration, not the sole design objective. - **documented**: Code review: Review should vary with experience, change size and criticality rather than automatically apply the heaviest process to every change. Newcomers particularly benefit from review; an experienced maintainer's small, low-risk change may not justify it. Review also transfers knowledge in both directions: a junior reviewer can expose a senior's unstated assumptions. This is a judgment about cost and learning, not permission to ignore risk. - **documented**: Frontend architecture: For many information systems, begin with server-rendered HTML and add client behavior where interaction actually needs it. - **documented**: Performance: Separate request latency, aggregate throughput and cost. His approximate web-response heuristics are below 300 ms and ideally around 100 ms; they are not universal service-level objectives. Once individual requests are fast enough, network, assets and developer time may matter more. Later, he noted that cheaper implementation can make even small per-request savings worthwhile across millions of requests, despite little visible latency difference for a single user. - **documented**: Caching: Use model identity and update timestamps in cache keys so changed records naturally receive new keys, and nest fragments so unaffected siblings remain reusable. Propagate changes to ancestor keys and account for template changes. Shared cached HTML may be decorated for presentation, but client-side hiding must not protect confidential content; authorization remains server-side and private data needs an appropriate cache boundary. These are 2013 Basecamp patterns, not a substitute for measuring a current workload. - **documented**: Databases, queues and hardware: Revisit specialized infrastructure when hardware changes. - **documented**: Cloud versus owned infrastructure: His earlier expectation was that renting would be simpler and cheaper; after examining bills and operations, he favored ownership for 37signals' predictable demand. - **documented**: Elasticity and serverless: Fine-grained rental can make sense for occasional work and rapid, unpredictable scaling. - **documented**: AI-assisted programming: His earlier position favored personally typing code and using AI as an explainer or pair programmer, partly because typing helped him learn.
