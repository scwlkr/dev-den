# David Heinemeier Hansson (DHH): positions

Built from 79 accepted distinct works and 321,087 source words. Compiled reasoning with source support and limits below.

- **documented**: Monoliths and service boundaries. DHH’s default is an integrated monolith, not a distributed system assembled in anticipation of scale. In-process calls avoid network failure, latency, retries and coordinated releases. In his recovery strategy, stop creating services, choose a center for new work, and consolidate critical flows first. Extract a well-bounded component when substantial measured performance or organizational benefits justify the boundary; he accepts that exceptions exist. His rough code-size judgments are prompts to examine comprehension, not universal limits. - **documented**: Framework scope. Rails is designed primarily to let an individual or small team build a complete, database-backed web application. Its breadth and integrated defaults reduce gaps between libraries, but make the framework itself larger and less sharply bounded. Shopify demonstrates that Rails can grow much further; it does not change his stated primary design target from the individual starting out. He also supports API-only Rails as a compatible secondary use. - **documented**: Conventions and defaults. Choose a coherent default for routine decisions, then allow substitution when a real requirement warrants it. Shared naming assumptions can support deeper abstractions and reduce repeated configuration, but departures carry integration and learning costs. This is not an argument that application-specific differences never matter; it is a request to spend attention on the differences that do. - **documented**: Framework extraction. Build for a real application first, identify recurring pain, and generalize what has survived use. DHH says speculative framework invention produced some of his own bad features. Basecamp remains an important source of Rails ideas, but he also acknowledges the wider contributor community. Before promoting an alternative to a default, he wants evidence from a consequential application rather than a toy alone. - **documented**: Active Record and SQL. For database-backed applications, he favors mapping tables to classes and rows to objects, combining persistence and domain behavior rather than insisting on a pure object model. The payoff is less wiring and a useful relationship DSL; the cost is accepting database-shaped constraints. He rejects hiding the relational model completely and expects developers to learn SQL, with direct SQL as an escape valve when object mapping is awkward. - **documented**: CRUD and domain modeling. Resource conventions are a productive constraint: if an operation seems to require an unusual controller action, look for a missing domain concept such as membership or subscription. A named object can own authorization, validation or history. Do not force the model when the additional object has no useful independent concerns; he allows a direct close action for a simple state transition. - **documented**: Server rendering and client complexity. For document-oriented applications, he prefers server-rendered HTML with targeted JavaScript to duplicating the presentation stack in a full client application. Turbo and Stimulus are intended to improve navigation and interaction without making a separate SPA mandatory. Highly interactive interfaces can justify localized client-side techniques or an SPA; the relevant question is whether the user experience repays the additional stack. - **documented**: Web, hybrid and native clients. His earlier Hotwire position favored web views with native controls: a small team could ship across platforms while avoiding repeated native implementations and some app-store release coordination. - **documented**: Caching. Key-based expiration and nested fragments make cache maintenance less dependent on manually remembering every invalidation. A changed leaf updates its key and relevant ancestors, while unchanged siblings remain reusable; template changes also need to affect keys. Shared cached HTML can be decorated for presentation, but client-side hiding is not a confidentiality boundary. Private data requires an appropriately separated cache and server-side authorization. - **documented**: Database-backed infrastructure. Solid Cache reflects his view that fast SSDs can make disk-backed fragment caching preferable to RAM-limited Redis caching for Basecamp and HEY. Solid Queue applies a similar argument to jobs, using database transactions and, where available, SKIP LOCKED. He explicitly describes lower throughput on SQLite than on supported MySQL or PostgreSQL configurations. These are workload-dependent trade-offs, not proof that a database should replace every specialized service. - **documented**: Query latency and throughput. Separate the time and cost of one request from aggregate throughput. In the 2025 interview, DHH describes roughly 100 ms as a practical target and suggests getting below at least 300 ms, while identifying databases as a harder scaling constraint than horizontally adding application servers. Rails 7 also offered concurrent loading for unrelated queries; its three 100 ms queries completing in 100 ms is an idealized example, not a promise. - **documented**: Runtime cost versus programmer time. Ruby is a deliberate luxury when developer productivity and comprehensibility are worth more than extra compute. In one historical example, application servers were about 15% of operating cost, so halving that component had to be compared with a modest productivity difference. He excepts low-value requests and genuinely low-level workloads. He also recommends benchmarking an isolated performance service before accepting its productivity and coordination cost. - **documented**: Cloud versus owned hardware. DHH moved from embracing rented capacity to favoring ownership for 37signals’ predictable, substantial workload. Compare actual cloud commitments and managed-service costs with hardware, facilities, staff, support, redundancy and opportunity cost. Cloud remains attractive for very small or uncertain businesses and extreme spikes; his FAQ suggests frequent 5–10× or greater peaks may justify cloud or a mixed baseline-and-spike strategy. Existing staff and rack capacity materially helped his own case. - **documented**: Operations and reliability. Owning servers does not require building a data center: 37signals rents facilities and pays external staff to rack and service equipment. DHH reports that the internal operations team did not grow after the exit, while emphasizing that operating the services still requires substantial work. Their intended reliability design uses two geographically separated sites, each sized for the load, and replicas of critical infrastructure; this is a design description, not an availability measurement. - **documented**: Deployment complexity. Containers are valuable for packaging applications and dependencies, but DHH considers Kubernetes an excessive operational burden for the deployment job 37signals needed to do. Its alternative combines KVM, Docker and Kamal for deployment and rollback. He acknowledges that Kubernetes offers sophistication and standardization for large operators; the recommendation is to match the machinery to the actual deployment problem. - **documented**: Single tenancy and SQLite. DHH proposes that an individual customer’s information system can have much simpler scaling needs than a multi-tenant service serving all customers together. ONCE was presented as an experiment in customer-operated, single-tenant products, potentially using SQLite. - **documented**: Testing and test-driven design. By 2014, DHH had rejected test-first as a universal design discipline after finding that some test-driven designs were harder for him to understand. He did not reject automated tests: database-backed model tests and system tests can cover interactions that isolated units miss. Test-first remains useful when inputs and expected outputs are clear. His later regret about dismissing TDD as faith-based qualifies the rhetoric, not a reversal into mandatory TDD. - **documented**: Types, metaprogramming and readability. He favors dynamic Ruby partly because annotations and type gymnastics can interfere with his metaprogramming style, and he removed TypeScript from Turbo. - **documented**: AI-assisted programming has changed his own practice. An earlier position favored using AI for lookup and advice while personally typing, partly because typing helped him learn; he even said he would retire before permanently giving up the keyboard. - **documented**: Teams, focus and review. His feature-team default is one programmer and one designer, with work inspected and adjusted as it progresses.
