- **documented**: Convention over configuration. Parts: identify recurring choices, select a dependable convention, let related abstractions rely on it, and retain an escape hatch. Use it when teams repeatedly decide inconsequential details such as table and foreign-key names. Prefer the default when an exception adds little domain value; account for the ongoing cost of losing shared assumptions before departing. An unusual legacy schema or a genuinely important application requirement can justify the exception. The benefit is cumulative: one naming convention can also support association inference and make unfamiliar applications easier to navigate. - **documented**: Omakase and conceptual compression. Parts: supply a coherent full-stack starting package, integrate its components, hide recurring incidental decisions, and allow substitutions when needs warrant them. Use for a new web application or team that would otherwise assemble and debug a unique collection of tools. Judge the whole development path, not merely the size of each library: a larger framework can make the finished application simpler by absorbing integration work. The cost is a broad framework surface and implicit behavior that developers must eventually learn; defaults are not mandatory choices. - **documented**: One-person framework. Start with a realistic end-to-end job: build, ship, and maintain a modern application. Ask which concepts, specialist handoffs, and infrastructure subscriptions prevent a capable generalist from completing it; compress or integrate the recurring ones. Use this lens for framework defaults and small-team architecture, not as a claim that one person can master every large system. Rails is principally optimized for an individual starting out, even though it can support much larger businesses. The relevant test is whether the complete workflow becomes understandable and usable, not whether every component is minimal. - **documented**: Framework extraction. Build for a concrete product need, observe recurring pain in real use, extract a reusable solution, and evaluate the resulting API against application code. Use when considering a framework feature, library, or deployment tool. A production need provides a stopping condition: stop adding machinery when the pain is resolved. DHH says some of his speculative framework inventions became bad features, so generality alone is not evidence of value. Extraction from one product can still miss other users' needs; Rails also incorporates contributions and requirements from its wider ecosystem. - **documented**: Monolith-first and service-extraction test. Begin with an integrated system and partition internally using programming constructs. Consider extracting only after identifying a bounded module without critical-flow dependencies and a substantial, articulated performance or organizational benefit. Count network failure, latency, retries, synchronization, deployment coordination, and loss of whole-system comprehension as costs. DHH treats Basecamp and HEY at just over 100,000 Ruby lines as individually comprehensible and suggests that comprehension breaks down at substantially larger sizes; these are rough personal judgments, not line-count thresholds to enforce. Large organizations and exceptional workloads may justify distribution. - **documented**: Microservice recovery. First stop adding services. Pick an existing service as the center for new functionality, then consolidate dependent critical flows such as signup or checkout before isolated components. Reduce unnecessary language and dependency diversity, and use modules and namespaces to organize the resulting system. Leave an independently justified performance hotspot until later: DHH accepts a faster-language service when measurement establishes that its gain outweighs productivity costs. This is a migration direction, not evidence that every service can safely be merged without a separate data and deployment plan. - **documented**: CRUD as a modeling constraint. Express a resource through conventional operations and ask whether an awkward custom action reveals a missing domain concept. Use this to make controllers predictable and to discover meaningful entities, not to force every action into an artificial resource. In DHH's closure example, a direct close action can be sufficient when little more than a timestamp is involved; a closure event or state object becomes more attractive when independent concerns accumulate. - **documented**: Active Record with relational awareness. Map tables to classes and rows to objects; use associations and domain methods to avoid repetitive wiring while keeping persistence visible. This is useful for database-backed business applications whose domain and storage needs usually travel together. Do not treat an object mapping as permission to ignore SQL: learn the database and use direct queries when the abstraction becomes awkward. The trade-off is less separation than a pure data mapper, in exchange for simpler wiring and faster application development. - **documented**: Clarity-first testing. Compare actual code alternatives for readability and conceptual overhead, then select tests that give the required confidence. Model tests can exercise the database and system tests can check assembled behavior; fixtures can represent a useful world of related records. Test-first is appropriate when expected inputs and outputs are already clear, but DHH rejects making it the universal design discipline. In particular, do not introduce multiple layers of dependency injection or command objects solely to make isolated tests faster if the resulting application becomes harder to understand. - **documented**: Latency, throughput, and productivity economics. Separate single-request latency, cost per request, and total throughput before selecting a language or optimization. DHH's practical target for his applications is roughly 100 ms, with a suggested ceiling below 300 ms; neither is a universal service-level objective. Application servers can often be added horizontally, while database capacity may be a harder constraint. In his historical example, Ruby application servers represented about 15% of operating cost, so halving that portion had to be weighed against developer productivity. Low-value requests and low-level workloads can reverse the calculation. - **documented**: Russian-doll caching. Derive fragment keys from record identity and update state, nest cached fragments, and propagate changes to parent records so an edited leaf invalidates relevant ancestors while siblings remain reusable. Include template digests and dependencies so changes in presentation also change the applicable keys; declare dependencies when automatic discovery misses them. Use for document-oriented pages with repeated rendering work. Shared HTML must not contain private data that is merely hidden in the browser: enforce authorization server-side and use finer-grained caching for confidential content. - **documented**: Criticality ladder for infrastructure migration. Start with a low-criticality application, settle operational questions there, and then move more important systems. Within a complex application, move components separately where possible and preserve a rollback path. Proximity between cloud and colocated hardware can keep cross-boundary database latency low enough for partial moves; otherwise a staged architecture may be impractical. After the push, repair shortcuts, stabilize processes, and let the team recuperate. - **documented**: Product-driven rewrite. First test whether the existing code can accommodate the intended design.
