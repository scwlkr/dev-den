# David Heinemeier Hansson (DHH): frameworks

Built from 200 accepted distinct works and 505,611 source words. Compiled reasoning with source support and limits below.

- **documented**: Convention over configuration. Parts: identify choices common to many applications; select a predictable default; use that shared assumption to enable further abstractions; preserve an escape route for meaningful exceptions. For example, Rails can infer a table and association from naming conventions. Use this when repeated configuration consumes attention without differentiating the product. Prefer the convention unless the application-specific benefit of departing from it outweighs the cost of surprise, integration work and lost shared knowledge. This is a judgment, not a numerical scoring rule. - **documented**: Omakase and conceptual compression. Parts: provide an integrated, working selection; make its pieces cooperate; remove setup and specialist knowledge from the initial path; allow substitutions when a real need arises. Evaluate simplicity across the complete application, not by counting the framework’s components. A bigger toolkit can be simpler if it prevents users from assembling and maintaining many separate pieces. The trade-off is accepting someone else’s defaults and a potentially large framework surface. DHH does not claim his selections are inherently superior for every team. - **documented**: Extraction from real applications. Parts: build a product for a concrete need; notice recurring pain; extract the reusable mechanism; compare real application code before and after; stop when the pain is resolved. Use it when considering a framework feature, internal platform or library. The decision bar is demonstrable improvement in an actual use case, not the number of hypothetical consumers. DHH says his own speculative ideas have sometimes failed that test. A single application can also give a framework blind spots, so consider wider users without pretending every request belongs in core. - **documented**: Majestic monolith and service extraction. Parts: start with an integrated application; organize internally with modules and namespaces; preserve the ability of a small team to understand and change complete flows. Extract only after identifying a bounded module and articulating a substantial performance or organizational benefit. DHH particularly warns against putting critical dependent flows across network boundaries, which add latency, failure handling and coordination. He accepts that exceptionally large organizations may benefit from service boundaries. His line-count and staffing examples are rough observations, not universal breaking points. - **documented**: Recovering from premature microservices. Parts: stop creating additional services; choose an existing service as the center of new work; consolidate highly coupled customer flows first; retain isolated, measured performance hotspots until last; reduce unnecessary language and dependency diversity. Use this when a small team spends more effort coordinating deployments and remote calls than changing the product. Benchmark a proposed high-performance satellite against the productivity it costs. This is a migration direction, not evidence that every service should be merged or that a rewrite alone repairs poor engineering habits. - **documented**: CRUD as a modeling prompt. Parts: express ordinary operations through resources and conventional controller actions; when an operation fits awkwardly, ask whether the domain contains a missing concept; keep required domain side effects out of the controller; stop modeling when the additional concept does not earn its complexity. A case-closing operation with only a timestamp may justify a simple action, while a richer independent closure concept may justify its own model. CRUD is a constraint for discovering useful language, not a rule that every behavior must be forced into the same shape. - **documented**: Active Record with relational awareness. Parts: map tables to classes and rows to objects; use associations and domain behavior to reduce repetitive plumbing; learn SQL and use it directly when the abstraction is awkward. The decision is not whether a pure domain model has cleaner theoretical boundaries, but whether those boundaries improve the actual database-backed application enough to justify their wiring. DHH deliberately combines persistence and domain logic, accepting constraints on object purity. This is a fit judgment for his class of web applications, not a denial of other persistence patterns. - **documented**: Progressive server-rendered interaction. Parts: start with server-rendered HTML and ordinary request-response flows; use Turbo navigation for responsiveness; add Frames or Streams for scoped updates; use Stimulus for local behavior; introduce richer client architecture where the interaction truly requires it. Use this for document-oriented information systems where duplicating presentation and state across a separate client and API would add coordination. DHH concedes that a sophisticated client can be simpler when the interface genuinely demands it. Rails 7 also allowed bundlers where a no-build path was unsuitable. - **documented**: Russian-doll caching. Parts: derive fragment keys from record identity and update state; nest fragments; propagate updates through the parent hierarchy; include template digests and declare dependencies the framework cannot infer. An updated leaf changes ancestor keys, while unaffected sibling fragments remain reusable. Use it for server-rendered pages with repeated, partially changing content and a cache that can evict old entries. DHH distinguishes presentation decoration from access control: client-side hiding can conceal a button, but confidential content must not be sent to an unauthorized browser. - **documented**: Performance and productivity economics. Parts: distinguish single-request latency, cost per request and total throughput; measure the actual bottleneck; compare runtime savings with programmer time and product opportunity. DHH’s approximate web heuristic is to get below 300 ms and aim around 100 ms where practical, not to treat either figure as an SLA. His historical example put Ruby application servers at roughly 15% of operating budget, so even halving that portion had to compete with developer productivity. Low-value requests, low-level workloads and high volume can change the calculation. - **documented**: Cloud versus ownership calculation. Parts: separate sustained baseline from variable demand; price equivalent compute, storage, redundancy, operations staff, facilities, bandwidth, support and capital over an assumed useful life; include migration and opportunity costs; test sensitivities. DHH’s five-year illustration compared about $2.3 million a year in selected cloud services with roughly $840,000 annually for hardware amortization and existing facilities, excluding the separate S3 move. - **documented**: Criticality ladder. Parts: identify the consequence of failure, from threats to life and major financial loss down through data loss, access loss and inconvenience; choose review, testing and rollout rigor accordingly; make proportionate risk-taking safe for the team. For early low-stakes product discovery, speed can matter more than maximal process. For safety-critical work, that reasoning does not transfer. Also consider change volume: moving from five to fifty changes per week can increase total incidents even if each change becomes less likely to fail. - **documented**: From pitch to real use, unnamed. Parts: begin with a sketch or pitch; run a technical spike against the existing architecture; build an interactive version; use it with messy real data; renegotiate expensive elements with the designer. Each step exposes assumptions that prose and static mockups can hide. Use it when disagreement is abstract or the team is unsure whether an attractive design fits its materials. - **documented**: Code as a draft: the four Cs. Parts: make a solution work, then revisit the whole change for clarity, cohesion, consistency and conciseness; inspect names, abstraction levels and proportion; remove concepts that do not earn their keep. A pull request can support self-review as well as peer review. Favor a cohesive scope rather than assuming every large change is bad. Concise is not maximally compressed: code that saves characters but becomes unreadable fails the human-reader test. DHH treats taste as trainable through reading, writing and revision rather than as an objective score. - **documented**: Test for confidence, not architectural purity. Parts: choose model, controller and system tests for the interactions that matter; allow model tests to exercise the real database; avoid repeating every assertion at every layer; use test-first when the input and expected output are already clear. DHH moved away from making test-first his default because he found test-driven isolation could add indirection and distort design. He did not abandon automated tests. CI and coverage increase confidence rather than proving correctness, so match extra procedure to risk and maintenance cost.
